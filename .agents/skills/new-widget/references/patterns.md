# 반복 패턴

기존 위젯 3종(Jira / Web / Todo)에서 **실제로 반복된** 것만 모았다.
"이렇게 하면 좋겠다"가 아니라 "이렇게 해서 문제를 겪었거나 피했다"는 기록이다.

---

## 데이터 경로 3형태

### A. 외부 API — Jira

```
Rust provider(client·types·error) → 캐시 → IPC 커맨드 → useJiraData 훅 → envelope → View
```

- **캐시 우선 표시.** 앱 시작 시 `jira_cached()`로 디스크 캐시를 먼저 그리고,
  그 뒤에 `jira_fetch()`가 조용히 갱신한다. 빈 화면 + 스피너로 시작하지 않는다
- 실패해도 직전 데이터를 유지하고 "N분 전" 흐린 표시만 더한다
- **일시적/영구적을 Rust가 분류해서 내려준다** (`kind: "transient" | "permanent"`).
  프론트가 상태코드를 보고 판단하지 않는다

### B. 로컬 파일 — Todo *(`todo-widget` 브랜치)*

```
Rust storage → IPC 커맨드(전체 목록 반환) → zustand 스토어 → View
```

- envelope을 쓰지 않는다. 위젯이 하나뿐이고 로딩이 사실상 없다
- **커맨드가 매번 전체 목록을 돌려준다** — 부분 갱신 로직이 없으면 어긋날 수 없다
- 낙관적 업데이트를 하지 않는다. 디스크는 수 ms고, 유일본 데이터에서 실패를
  숨기는 게 더 위험하다

### C. 자체 로드 — Web

```
위젯이 스스로 (iframe) — envelope은 껍데기
```

- 우리가 로드 성공/실패를 알 수 없다. **알 수 없다는 사실을 문서와 UI에 적었다**
- 새로고침 = remount용 key 증가

## 상태를 화면에 드러내는 법

`WidgetStatus` 7종을 쓴다. 새 상태를 만들기 전에 기존 것으로 되는지 본다.

| 상태 | 언제 | 본문 |
|---|---|---|
| `idle` / `loading` | 첫 로드, 보여줄 게 없음 | "불러오는 중…" |
| `ready` | 정상 | 데이터 |
| `empty` | 정상인데 0건 | "조건에 맞는 …이 없습니다" |
| `stale` | 갱신 실패, 직전 데이터 있음 | **데이터 유지** + 헤더 앰버 |
| `error-transient` | 429/5xx/네트워크 | **데이터 유지** + 하단 "갱신 실패 — 재시도 중" |
| `error-permanent` | 401/403/400 | 본문을 에러로 + **무엇을 해야 하는지** + 행동 버튼 |

**핵심:** 한 번 데이터가 그려진 뒤로는 본문을 비우지 않는다.

**인증 실패는 전역 배너 한 번만.** 위젯이 4개면 같은 401이 4번 뜨는데 그건 소음이다.
`useConnectionStore.setJiraAuthFailed(true)`로 올린다 (DECISIONS 16장).

## 밀도 — 폭에 따라 표현을 바꾼다

`WidgetViewProps.width`는 **픽셀**이다(그리드 열 수가 아니다). 같은 열 수라도
창 크기에 따라 폭이 다르기 때문.

Jira의 기준(DESIGN 4.7, 실측):

```ts
if (width < 300) return 'compact'   // 상태를 점으로 축약
if (width < 420) return 'normal'    // 텍스트 배지
return 'wide'                        // 담당자 이름까지
```

**밀도 경계는 추측하지 말고 실측한다.** 스크린샷을 눈으로 보고 정하면 여러 번
헛짚는다 — `alignment.test.tsx`가 좌표를 직접 재서 고정한 결과다.

## 순수 함수로 빼는 기준

**"테스트하고 싶은가"**가 기준이다. 렌더 트리를 거쳐야 검증되는 로직은 이미
잘못 놓인 것이다.

기존 사례:
- `columns.ts` — 열 폭·정렬 계산
- `blocked.ts` — 임베드 차단 도메인 판정
- `plainTextToAdf.ts` — 평문 → ADF 변환
- `issueKeys.ts` — 텍스트에서 티켓 키 추출
- `store/todos.ts`의 `dateKey`·`addDays`·`daysSinceOrigin` *(todo-widget 브랜치)*

Rust 쪽도 같다: `scope_to_projects`, `reconcile_with_meta`는 전부 `State`를
안 받게 뽑아서 앱 없이 테스트한다.

## 날짜를 다룰 때 (Todo에서 겪은 것)

> 아래 파일 경로는 `todo-widget` 브랜치 기준이다. main에 머지되기 전이라면
> 그 브랜치에서 확인할 것.

**`toISOString()`을 쓰지 마라.** UTC라 한국 시간 오전 9시 이전이면 어제가 나온다.

**`new Date("2026-08-01")`도 쓰지 마라.** UTC 자정으로 파싱돼 한국에서 오전 9시가 된다.

둘 중 하나만 써도 **자정 직후에 하루가 밀린다.** 로컬 기준 헬퍼를 만들고
테스트로 고정한다 (`store/todos.ts`의 `dateKey`/`parseDateKey`).

**자정 감지는 `setTimeout`이 아니라 폴링으로.** macOS는 잠자기 중 타이머를
정지시켜서, 노트북을 덮고 다음 날 열면 안 깬다. `useNow()`가 이미 1분마다
도므로 날짜 문자열이 바뀌었는지만 보면 된다 — 잠자기·시간대 변경·수동 시계
조정에 전부 견딘다.

## 쓰기가 있는 위젯

### 멱등하지 않으면 재시도 금지

Jira 티켓 생성이 그 사례다. 네트워크·타임아웃·5xx는 **요청이 닿았는지 알 수 없다.**
재시도하면 티켓이 두 개가 되고 우리에겐 지우는 기능이 없다.

```
400 계열 → 스키마 재조회 후 1회만 재시도 (고칠 게 있을 때만)
401/403/404 → 재시도 없음
429/5xx/네트워크 → 재시도 없음 + possibly_created: true + 버튼 잠금
```

### 되돌리기를 만들 거면 저장할 상태를 먼저 확인한다

Todo 이월은 `CarryOverReport`(이전 날짜·카운트)를 들고 있어서 되돌릴 수 있다.
반면 **삭제 되돌리기**는 배열 인덱스까지 기억해야 하고 그 사이 다른 항목이
추가되면 어긋난다 — 그래서 "완료 항목 정리"를 삭제가 아니라 **접기**로 바꿨다.
*(Todo 이월·접기는 `todo-widget` 브랜치)*

**되돌릴 수 없으면 되돌릴 수 없다고 화면에 적는다.**

---

## 토스트를 쓰지 않는다 (DESIGN 5.3)

성공도 실패도 토스트로 알리지 않는다. 사라지는 알림은 놓친다.

- 생성 성공 → **모달을 닫지 않고** 성공 화면으로 바꾼다 + 다음 행동 버튼
- 이월 발생 → 위젯 상단 인라인 배너, **자동 소멸 없음**
- 갱신 실패 → 위젯 하단 한 줄

## 설정 폼

`ConfigForm`은 **무엇을 가져올지**를 정하는 곳이다. Todo처럼 가져올 게 하나뿐이면
제목만 두고 나머지는 위젯 본문의 상호작용으로 옮긴다(날짜는 헤더의 `◀ ▶`).

외부 목록(프로젝트 등)이 필요하면:
- **디스크 캐시 + 명시적 ↻ 버튼.** 자동 갱신하지 않는다
- ↻ 옆에 "N일 전"을 상대시각으로 적는다 — 언제 받은 건지 알아야 판단한다
- **같은 데이터를 두 경로로 가져오지 않는다.** 설정창과 생성 폼이 같은 캐시를 본다
