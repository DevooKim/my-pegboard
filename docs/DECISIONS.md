## 0. 제품의 정의

**my-pegboard** — 페그보드처럼 위젯을 자유롭게 배치하는 개인용 데스크톱 대시보드.

**존재 이유 (성공 기준):**
여러 도구에 흩어진 내 작업을 **한 화면에서 즉시** 보는 것.
각 서비스의 웹 UI를 열어 기다리는 것보다 빨라야 값어치가 있다.
**속도가 기능보다 우선한다.**

**사용 맥락:** 각자 자기 기기에서 자기 계정으로 쓰는 단일 사용자 도구.

## 1. 실행 형태 — Tauri 데스크톱 앱

**결정:** Tauri 2 데스크톱 앱. 창 기반으로 시작, 트레이 상주는 후속.

**폐기한 것:** PWA + 로컬 서버 (초기 요구사항이었음)

**왜 PWA를 버렸나:**
- 사용자가 PWA를 원한 진짜 이유는 "앱처럼 쓰고 싶어서"였다. Tauri가 그 목적의 직행로.
- "로컬 전용"이 확정되면서 PWA의 이점(타 기기 접속, 오프라인)이 대부분 무의미해짐.
- 메모리 요구사항과 정면 충돌: 웹앱은 Node 서버(40~80MB) + 브라우저 탭(80~150MB).
- CORS 프록시 레이어 전체가 불필요해짐 → 버그 표면적 감소.

**푸시 알림 관련:** Tauri는 로컬 알림(`tauri-plugin-notification`)을 네이티브로 지원.
원격 푸시(APNs)는 불가하지만 **로컬 전용 앱에는 애초에 불가능**하므로 손실 없음.

**포기한 것 (알고 선택함):**
- 폰/태블릿에서 볼 수 없음
- 앱을 완전히 종료하면 폴링 중단 (트레이 상주로 완화 가능, 4차)

## 2. 배치 모델 — 12열 그리드 스냅

**결정:** `react-grid-layout` v2. 12열 격자, 드래그 시 밀어내기 + 자동 정렬(compact).

**대안 검토:**
- 자유 캔버스(Figma형): 창 크기 변화에 취약. 대시보드 콘텐츠는 리스트라 공간적 의미가 없음.
- 그리드 + 겹침 허용: 실사용에서 위젯이 실수로 겹쳐 가려짐.
- Masonry/Bento: "자유 배치" 요구를 포기하는 선택.

**직접 구현하지 않는 이유:** 충돌 해결·연쇄 이동·compact 알고리즘은 검증된 구현이 낫다.
번들 25KB(gzip)는 Tauri 앱 메모리 예산에서 무의미한 수치.

**주의:** RGL은 레이아웃(x,y,w,h)만 관리. 위젯 내용물의 렌더링 성능은 별도 책임.

## 3. 위젯 모델 — 인스턴스형

**결정:** 위젯 = 쿼리 하나. 같은 타입을 여러 개 배치 가능.

**사용자 실제 요구:** "우리 팀 티켓"과 "내 티켓"을 각각 보고 싶다.

**개수 제한 (타입별):**
| 타입 | 최대 |
|---|---|
| Jira | 4 |
| GitHub | 4 |
| Todo | **1** |
| Web | 4 |
| 앨범 | 4 |

**타입별로 나눈 이유:** 부담의 성격이 다름. Jira 10개는 rate limit에 걸린다.
전체 제한으로 하면 한 타입을 많이 쓰는 사용자가 다른 타입을 못 놓는 상황이 생김.

**Todo만 1개인 이유 (2026-08-01 수정):** 부담이 아니라 **의미** 때문이다.
모든 Todo 위젯이 같은 `todos.json`을 읽으므로 두 번째 위젯은 같은 목록을 한 번 더
그릴 뿐이다. 얻는 것 없이 위젯 간 동기화 비용만 생긴다. 처음 8로 정한 것은
"Todo는 API 비용이 없으니 많이 놔도 된다"는 근거였는데, 그건 **놓을 수 있는
이유**이지 **놓을 만한 이유**가 아니었다. 날짜를 나란히 보고 싶으면 헤더의
`◀ ▶`로 옮긴다.

**앨범이 4개인 이유 (2026-08-06):** 같은 기준을 반대로 적용한 결과다. 앨범은
**폴더가 다르면 다른 내용**이므로 여행 사진과 작업 스크린샷을 나란히 놓는 것에
의미가 있다. API 비용이 없다는 점은 Todo와 같지만, 그건 앞서 적은 대로 판단
근거가 아니다 (24.10장).

**따라오는 과제:** 같은 서비스를 보는 위젯이 여러 개면 API 호출도 배수.
→ Rust 캐시 계층에서 요청 중복 제거 필요.

## 4. 위젯 등록 구조 — 인터페이스 + 레지스트리

**결정:** 모든 위젯이 공통 계약을 구현하고 레지스트리에 등록.
공통 껍데기(`WidgetShell`)가 헤더/새로고침/상태/에러/설정/삭제를 처리, 위젯은 내용물만 그림.

**왜:** 위젯 3종이 전부 "외부 API에서 목록을 주기적으로 가져와 표시"라는 같은 골격.
개별 구현하면 "Jira 위젯은 에러가 보이는데 GitHub 위젯은 조용히 실패" 같은 불일치가 생김.

**플러그인 시스템을 안 만든 이유:** 혼자 쓰는 앱. 동적 로딩은 보안·버전 호환 문제만 데려옴.

**설계 원칙:** 위젯 하나 = 프론트 폴더 하나 + Rust provider 하나.
새 위젯 추가 시 기존 위젯 코드를 열 필요가 없어야 함.

## 5. 데이터 소유권 — Rust가 주인

**결정:** Rust가 캐시·폴링·rate limit·재시도를 전부 소유. React는 표시만.
Rust가 이벤트를 push하면 해당 위젯만 리렌더.

**따라서 안 쓰는 것:** TanStack Query, TanStack DB

**TanStack Query를 안 쓰는 이유:**
그것이 해주는 일(캐시·중복제거·재시도·백그라운드 갱신)을 Rust가 더 좋은 위치에서 한다.
두 군데 캐시를 두면 "왜 이 값이 안 바뀌지"를 두 배로 디버깅하게 됨.

**TanStack DB를 안 쓰는 이유 (검토했음):**
- `@tanstack/react-db@0.1.x` — 1.0 이전, API 변경 위험
- 킬러 기능(낙관적 업데이트·sync)이 우리에게 불필요: 데이터가 거의 읽기 전용
- 증분 쿼리 엔진(IVM)은 수만 행에서 값어치. 우리는 위젯당 30건, 전체 ~120건
- Rust 소유 원칙과 충돌 → 양쪽 힙에 데이터 이중화

**TanStack DB가 겨냥한 실제 문제("같은 티켓이 여러 위젯에 중복 저장")는 인정.**
→ Rust 쪽 `HashMap<IssueKey, Issue>` 키 기반 캐시 + 위젯은 키 목록만 보유로 해결.

**프론트 상태:** zustand. 위젯 배치와 UI 상태(모달, 선택)만.

**티켓 생성(쓰기)이 추가돼도 결론 유지:**
쓰기가 "티켓 생성" 하나뿐이라 낙관적 업데이트 프레임워크가 불필요.
생성 성공 → 해당 사이트를 보는 위젯 즉시 재조회로 충분.
오히려 Jira 생성은 필수 필드/권한으로 자주 실패하므로, 가짜로 넣었다 빼는 것보다 폼에 에러를 띄우는 게 정직.

## 6. API 호출 — Rust 커맨드

**결정:** 모든 외부 API 호출은 `#[tauri::command]`. `tauri-plugin-http`(프론트 fetch) 미사용.

**왜:**
1. **토큰이 WebView로 내려가지 않음.** 플러그인 방식은 JS가 토큰을 알아야 함 → 키체인의 의미가 반감.
2. **필드 축소.** Jira가 이슈당 200개 필드를 주지만 위젯엔 5개면 충분. Rust에서 걸러 IPC 페이로드를 1/10로.
3. **창을 닫아도 살아남음.** 트레이 상주(4차)로 갈 때 코드 이동이 없음.

**대가 (인정함):** Jira 응답 타입을 Rust struct로 정의해야 함. 필드 추가 시 Rust→커맨드→TS 3곳 수정.
→ `tauri-specta`로 완화.

## 7. 타입 동기화 — tauri-specta

**결정:** `specta` + `tauri-specta`로 Rust struct → TS 타입 + 타입 안전한 커맨드 호출 자동 생성.

**대안(수동 관리)을 안 쓰는 이유:** 타입이 5개 남짓이라 손으로 관리할 수도 있다.
그러나 커맨드 이름 오타·인자 누락·타입 불일치가 **런타임에야 드러난다.**
생성기를 한 번 세팅하면 그 전부가 컴파일 타임에 잡힌다.

**일반 원칙:**
> 초기 세팅 비용은 한 번이고 안전성은 영구적이다.
> 옵션을 고를 때 "만들기 번거롭다"보다 **"쓸 때 나쁜가"**와
> **"나중에 발목 잡는가"**를 먼저 본다.

## 8. 인증 — API 토큰 (Basic Auth)

**환경 확인 결과 (MCP 조회):**
- Atlassian **Cloud** 확정: `https://your-team.atlassian.net`
- cloudId: `00000000-0000-0000-0000-000000000000`
- → REST API **v3**, description은 **ADF JSON**, 사용자 식별자는 `accountId`

**결정:** Jira는 API 토큰 + Basic Auth (`email:token` Base64). GitHub은 fine-grained PAT.

**OAuth를 안 쓰는 이유:** 여러 사용자에게 배포하는 앱을 위한 것.
단일 사용자에게는 콜백 처리·refresh 갱신 비용만 있고 얻는 것이 없음.

**⚠️ 알려진 API 변경:** 구 `/rest/api/3/search`는 deprecated → `/rest/api/3/search/jql`.
신규 엔드포인트는 **total 개수를 주지 않음** (커서 기반 `nextPageToken`만).
→ "총 42건 중 30건" 같은 UI를 설계하지 말 것.

## 9. 비밀 저장 — macOS Keychain

**결정:** `keyring` crate. 토큰·이메일은 Keychain, 나머지는 JSON 파일.

| 데이터 | 저장소 |
|---|---|
| API 토큰, 이메일 | Keychain |
| 사이트 URL | 설정 파일 |
| 위젯 배치·config | `board.json` |
| Todo | `todos.json` (+ `.bak` 1세대) |
| API 응답 캐시 | 디스크 캐시 + Rust 메모리 |

**평문 파일을 거부한 이유:** 사용자 계정으로 실행되는 모든 프로세스가 읽을 수 있음
(설치한 npm 패키지의 postinstall 포함). 실재하는 공격 벡터.

**"파일 + 자체 암호화"를 거부한 이유:** 복호화 키를 어디 두나 — 순환 문제. 보안 연극.

**Keychain 폴백을 안 두는 이유:** 폴백이 조용히 발동하면 사용자가 자기 토큰이 평문인 걸 모름.
실패하면 실패했다고 말하는 게 낫다.

**비밀과 설정을 분리한 이유:** 설정 파일을 나중에 git에 넣거나 복사할 때 토큰이 딸려가는 사고 방지.

**네임스페이스:** `jira.default.token` 형태. 다중 연결(4차) 대비.

## 10. 저장 형식 — JSON 파일 분리

**결정:** `board.json` + `todos.json`. SQLite 미사용.

**규모 근거:** 위젯 최대 16개(config 각 수백 바이트), Todo 연간 수천 개 = 수백 KB.
이 규모에서 SQLite는 스키마 마이그레이션 부담만 추가.

**JSON의 실질 장점:** 사용자가 직접 열어서 고칠 수 있음. 배치가 꼬였을 때 파일 수정으로 복구.

**필수 안전장치 (빼먹으면 반드시 물림):**
1. **원자적 쓰기** — 임시 파일 → `rename`. 중간에 죽으면 배치가 통째로 날아감.
2. **디바운스** — 드래그 중 레이아웃 이벤트가 초당 수십 회. 500ms 디바운스 또는 드래그 종료 시 저장.
3. **스키마 버전** — `{ "version": 1, ... }`. 없으면 나중에 구조 변경 시 구파일을 읽을 방법이 없음.
4. **Todo 백업** — `todos.json.bak` 1세대. Todo는 유일본 데이터.

**SQLite로 옮길 시점:** Todo가 수만 개 / 전문 검색 필요 / API 응답 장기 캐시로 오프라인 지원.

**저장 위치:** `~/Library/Application Support/io.mypegboard.app/`

**다중 보드 대비 구조 (UI만 없음):**
```json
{ "version": 1, "activeBoardId": "default", "boards": [{ "id": "default", "name": "Board", "widgets": [] }] }
```

## 11. Jira 위젯

### 11.1 쿼리 설정 — 프리셋 + JQL 탈출구

**결정:** 프리셋 몇 개 제공 + "직접 입력"으로 JQL 열기.

**근거:** 사용자의 두 요구가 정확히 경계에 걸침.
- "내 티켓" → 프리셋으로 완벽히 커버 (`assignee = currentUser() AND resolution = Unresolved`)
- "우리 팀 티켓" → 프리셋 불가. "우리 팀"의 정의가 조직마다 다름(프로젝트/라벨/컴포넌트/사람 목록)

**폼 빌더를 거부한 이유:** AND/OR 중첩, 날짜 범위, 커스텀 필드로 끝없이 번짐.
그 끝에는 결국 JQL이 있다. Jira의 표현력을 UI로 재구현하는 일.

**후속 후보였던 것 → 구현됨 (2026-08-06):** Jira 저장된 필터 불러오기.

쿼리 선택지가 셋이 됐다: **프리셋 · 저장된 필터 · 생 JQL.**

이게 11.1의 원래 결정을 뒤집지 않는 이유: "우리 팀 티켓"의 정의를 우리가
표현하려는 시도가 아니라, **사용자가 이미 Jira에 표현해둔 것을 가져오는 것**이다.
폼 빌더를 거부한 근거(Jira의 표현력을 UI로 재구현하지 않는다)는 그대로 살아 있다.

#### `filter = <id>`로 서버에 넘긴다 — 추가 조회 0회

필터 id를 JQL로 풀기 위해 네트워크를 타지 않는다. `filter = 10001`은
**JQL 문법 자체**이고 Jira가 풀어준다. 그래서:

- `JiraQuery::to_jql()`이 **동기로 남는다.** 여기에 `async`가 붙으면
  호출하는 스케줄러·커맨드가 전부 따라 물든다. 위젯 하나당 필터 조회 1회가
  붙는 것은 시작 1초 목표(CLAUDE.md 성능표)를 정확히 깎는 종류의 비용이다.
- 만드는 JQL은 `filter = <id> ORDER BY updated DESC`.

**JQL을 복사해 굳히지 않는다.** 프리셋을 id로 저장하는 것과 같은 이유 —
Jira에서 필터를 고치면 위젯도 따라 고쳐지는 것이 "저장된 필터를 쓴다"의 의미다.

#### id와 함께 이름도 저장한다

```rust
JiraQuery::SavedFilter { id: String, name: String }
```

**진실의 원천은 id이고 `name`은 표시용 캐시다.** 프리셋은 정적 테이블이라
id→이름이 항상 풀리지만, 필터 이름은 서버에 있다. name 없이 저장하면
앱 시작 **0ms 시점에 위젯 제목이 "Jira"로 떴다가** 필터 목록이 도착한 뒤
바뀐다 — 깜빡임. 오프라인이거나 조회가 실패하면 영영 못 푼다.

대가: 서버에서 필터 이름을 바꾸면 이 값이 낡는다. 설정창에서 다시 고르면 갱신된다.
깜빡임을 없애는 값으로 싸다.

두 번째 용도는 **삭제된 필터**다. 필터가 지워지면 Jira가 400을 주고 기존
영구 에러 경로가 처리하는데, 원문에는 필터 id만 있다. 저장해둔 이름을 앞에
붙여 "저장된 필터 '우리 팀 스프린트': ..."로 보여준다 — 어느 필터가
사라졌는지 사용자가 알아야 한다.

#### 정렬·프로젝트 범위는 프리셋과 **같게** 적용한다

우리가 만든 JQL이 완결돼 있어서 `apply_sort`가 ORDER BY를 잘라 붙이는 것이
안전하고, `scope_to_projects`도 조건을 괄호로 감싸므로
`project IN ("ABC") AND (filter = 123)`이 된다. 생 JQL만 손대지 않는 원칙은 유지.

#### 목록 조회

`GET /rest/api/3/filter/search?expand=jql&maxResults=50`

- `/filter/favourite`가 아닌 이유: 즐겨찾기만이 아니라 **내가 만든 필터**도 필요하다.
- **설정창 쿼리 셀렉트를 열 때 1회.** 앱 시작 경로에 넣지 않는다 —
  위젯 렌더에 필요 없는 호출이다(config에 이름이 캐시돼 있다).
- 50건에서 끊는다. 넘겨서 스크롤하는 드롭다운은 이미 고를 수 없는 UI다.
- 에러 타입은 `JiraCallError`(모달·폼용 단발 호출). `JiraWidgetError`의
  `stale`이 늘 `None`이 되는 쪽은 맞지 않는다.

#### 실패해도 프리셋을 막지 않는다

필터는 서버에 물어봐야 하므로 실패할 수 있다(오프라인·권한·SSO).
그때 셀렉트 안에 인라인 에러 + [다시 시도]를 띄우되 **프리셋 항목은 그대로
선택 가능하다.** 새 기능이 원래 되던 일을 막는 것이 최악의 회귀다.
로딩 중에도 마찬가지다. (대전제 2 — 조용한 실패 금지, 그리고 실패가 선택을 잠그지 않는다)

#### 보안 — 필터 id는 숫자만

`filter = <id>`로 JQL에 그대로 들어가므로 인젝션 지점이다. 이스케이프가 아니라
**화이트리스트**로 막는다(`scope_to_projects`가 프로젝트 키를 다루는 것과 같은 판단).
숫자가 아니면 JQL을 만들지 않고 `None` → 영구 에러. 빈 JQL을 보내 전체 이슈를
긁어오는 조용한 오작동보다 명시적 에러가 낫다. 테스트로 고정했다.

**미검증:** `/filter/search` 응답 모양을 실측하지 못했다(구현 시점에 자격증명
접근이 막혀 있었다). 문서 기준으로 썼고 필드마다 `serde(default)`를 붙여
모양이 달라도 파싱이 통째로 실패하지 않게 했다. 실제 계정으로 한 번 확인할 것.

### 11.3 티켓 생성 — 최소 폼 + 필수 필드 자동 보강

**MCP로 확인한 사실 (2026-07-29):**

테스트한 사이트의 프로젝트 4개: `ABC`(Team), `XYZ`, `PRD`(제품관리, next-gen), `OPS`(Platform)

| 프로젝트 | 이슈타입 | 필수 필드 |
|---|---|---|
| ABC | `[Team] 기능`(10082) | project, issuetype, summary — **3개** |
| XYZ | `작업`(10007) | project, issuetype, summary, **reporter** — **4개** |

**→ 프로젝트마다 필수 필드가 실제로 다름이 확인됨.** 4개 중 2개만 봤는데 이미 갈림.
PRD은 next-gen(simplified) 타입이라 스키마가 또 다를 수 있음.

**동작:**
1. 폼 기본: 프로젝트 / 이슈타입 / 요약 / 설명(선택)
2. 프로젝트·타입 선택 시 `createmeta` 조회 → `required: true`인데 폼에 없는 필드를 추가로 렌더
3. `hasDefaultValue: true`인 필드(reporter, priority)는 서버에 맡기고 렌더하지 않음
4. createmeta 응답은 Rust에서 캐시

**부수 발견:** `allowedValues`에 우선순위·이슈타입 목록이 포함 → 드롭다운을 추가 API 호출 없이 채울 수 있음.

**동적 폼(createmeta 전면 의존)을 안 쓰는 이유:** Jira 커스텀 필드 타입이 수십 가지.
전부 대응하면 Jira 웹 폼을 재구현하게 됨 — 사용자가 도망쳐 나온 그것.

> **실측 정정 (2026-07-31).** 위 표의 "XYZ는 reporter까지 4개 필수"는 `hasDefaultValue`를
> 빠뜨린 서술이다. 실물 XYZ의 `reporter`는 `hasDefaultValue: true`라 **서버가 채운다.**
> 규칙 3(`hasDefaultValue: true`면 렌더하지 않는다)을 적용하면:
>
> | 프로젝트/타입 | required | 그중 폼에 그릴 것 |
> |---|---|---|
> | ABC `기능` | project, issuetype, summary | 3 |
> | XYZ `작업` | project, issuetype, summary, reporter | **3** (reporter 제외) |
> | PRD `작업` | project, summary | 2 |
> | (신규) `작업` | project, issuetype, summary | 3 |
>
> **네 조합 모두 동적으로 추가 렌더할 필드가 0개다.** 생성 가능한 프로젝트도 4개가
> 아니라 5개였다(문서에 없던 것이 하나 있다).
>
> 그래서 2번(동적 보강)은 지금 그릴 것이 없다. 그럼에도 남기는 이유는 **프로젝트 설정이
> 언제든 바뀌기 때문**이다. 필수 필드가 생기면 우리는 400을 받고서야 알게 되는데,
> 그때 createmeta를 재조회해 무엇이 빠졌는지 알려주는 것이 이 경로의 실제 역할이다.
> 즉 **렌더러가 아니라 경고·안전망**이다.
>
> 테스트 fixture `createmeta_edu.json`은 reporter를 `hasDefaultValue: false`로 적어놨는데
> 실물과 다르다. 고치지 않고 둔다 — 그 테스트가 검증하는 것은 "EDU의 현재 설정"이 아니라
> "기본값 없는 필수 필드를 폼이 집어내는가"라는 규칙이기 때문이다.

### 11.4 상세보기 — 모달 + ADF 직접 렌더러

**형태:** 전체 모달. ESC로 닫힘.
- 사이드 패널 거부: 12열 보드의 폭을 잠식
- 별도 창 거부: 창 관리 상태(중복 방지·위치 기억) 증가. 후속 옵션으로는 좋음

**내용:** 키/제목/상태/담당자/보고자/우선순위/라벨/생성·수정일 + description + **코멘트 목록**
(코멘트는 별도 API `/issue/{key}/comment`. 호출이 하나 늘지만 상세를 보는 이유의 절반)

**진입점 (2026-07-31 확정):** **행 전체**가 상세를 연다. `⌘+클릭`은 브라우저.
행 안의 키·상위 링크는 지금처럼 Jira로 나간다(DESIGN 4.6). 같은 행에서 목적지가
갈리는 것은 받아들인 대가다 — 링크는 링크답게 두는 쪽을 택했다.

**골격을 0ms에 그린다.** 목록이 이미 가진 값(제목·상태·담당자·우선순위·유형·날짜·
상위·스프린트)으로 모달을 즉시 채우고, 설명·코멘트·라벨·보고자만 나중에 채운다.
모달 전체를 스피너로 시작하면 "빠르게 보는 것"이라는 이 앱의 존재 이유가 무너진다.
**상세 결과는 디스크에 캐시하지 않는다** — 낡은 상세를 보여줄 바에는 잠깐 비는 편이 정직하다.

**코멘트:** 최신 **20건**을 받아 **대화 순서(시간 오름차순)로 전부** 표시한다. 접기 없음.
Jira에 `orderBy=-created`로 요청하고 Rust에서 뒤집는다 — 정렬 책임을 화면에 넘기지 않는다.
`total`이 더 많으면 "이전 N개는 Jira에서" 링크. (코멘트 엔드포인트는 구식 offset
페이지네이션이라 `total`을 준다. 검색과 다르다 — 8장 참조.)

**모달 안 티켓 전환:** 본문의 `PROJ-123`·`inlineCard`·**상위(parent)**를 누르면 창을
새로 열지 않고 그 티켓으로 갈아탄다. 뒤로가기 스택(`‹`)을 둔다.
**ESC는 모달 전체를 닫는다** — 스택을 한 겹씩 벗기지 않는다. 한 키가 두 가지 뜻을
가지면 사용자가 무엇이 일어날지 예측할 수 없다.

**부분 실패를 뭉개지 않는다:** 코멘트만 실패하면 설명은 그대로 두고 코멘트 자리에만
에러를 적는다. 하나가 죽었다고 본문 전체를 에러로 덮으면 볼 수 있었던 것까지 잃는다.

**ADF 렌더링 — 직접 구현 (의존성 0)**

선택지였던 것:
- `@atlaskit/renderer`: Atlaskit 디자인 시스템 전체를 끌고 옴. 메모리 요구와 정면 충돌
- `/rest/api/2` + `expand=renderedFields`로 서버 렌더 HTML 받기: 파싱 불필요하지만
  **HTML 구조·인라인 스타일을 통제할 수 없고, 동작을 붙일 수 없음**
  (코드블록 복사 버튼, 티켓 링크를 모달 내에서 전환 등)

**사용자가 "이 앱만의 UI"를 원해서 직접 렌더러 선택.**

1차 지원 노드:
- 블록: `paragraph` `heading` `bulletList` `orderedList` `listItem` `codeBlock` `blockquote` `panel` `rule` `table`(+row/cell/header)
- 인라인: `text` `hardBreak` `mention` `emoji` `inlineCard` `date`
- 마크: `strong` `em` `code` `strike` `underline` `link` `textColor` `subsup`

**미지원:** `mediaSingle`/`media` (이미지 첨부 — 인증된 URL 재요청 필요) → "이미지 N개, Jira에서 보기" 링크로 대체

**⚠️ 미지원 노드는 조용히 건너뛰지 말 것.** `[지원하지 않는 요소: mediaSingle]` 회색 플레이스홀더 표시.
안 그려진 것을 **모르는** 상태가 최악이다 — 내용이 빠졌다는 사실 자체가 보여야 한다.

**통제권을 택한 값어치:** 코드블록 복사 버튼, `PROJ-123` 링크는 모달 내 전환, 멘션은 자체 스타일 칩.

**하위 티켓 생성 — 상세에서만, 한 단계 아래만 (2026-08-01).**

에픽 상세에서 작업을, 작업 상세에서 하위 작업을 만든다. 버튼은 `＋ 하위 작업`
처럼 **만들어질 유형의 이름**을 그대로 달고 나온다.

계층은 `hierarchyLevel`로 정해진다(실측):

```
   1  에픽
   0  작업 · 기능 · 버그 · 스토리
  -1  하위 작업   (subtask: true)
```

규칙은 **바로 한 단계 아래**뿐이다. 두 단계를 건너뛰지 않는다 — 에픽 아래에
하위 작업을 직접 두는 것은 Jira가 거절한다. 하위 작업(-1) 아래로는 만들 수
있는 것이 없으므로 버튼도 안 나온다.

**목록에서는 하위 작업을 만들 수 없다.** 하위 작업은 "무엇의 아래인가"가
본질인데, 목록에는 그 맥락이 없다. 부모를 고르는 셀렉트를 폼에 넣으면
사용자가 도망쳐 나온 Jira 웹 폼을 재구현하는 쪽으로 한 걸음 간다.
상세 화면은 그 맥락을 이미 갖고 있다 — 지금 보고 있는 티켓이 부모다.

**계층 판정을 순수 함수로 뽑았다**(`childTypesFor`, `levelOf`). 틀리면 버튼이
안 나오거나(조용한 기능 상실) 만들 수 없는 유형을 제안해 400을 받는다.
둘 다 렌더 트리로 확인하기 번거로운 실패다.

> 상세 응답의 `issueType`에는 이름과 `subtask`만 있고 **`hierarchyLevel`이 없다.**
> 그래서 이름으로 프로젝트 유형 목록에서 레벨을 찾는다. 이름이 안 맞으면
> `subtask` 플래그로 근사하고, 그래도 모르면 **추측하지 않고** 버튼을 접는다.

### 11.5 티켓 조작 범위 — 읽기 + 생성 + 상태 변경

> **2026-08-06 개정.** 원래 "읽기 + 생성만"이었고 상태 변경을 뺐다. 그 조항이
> 스스로 열어둔 문("실사용 후 아쉬우면 추가")을 실사용이 통과했다. 아래는
> 개정된 결정이고, 뒤집힌 근거는 21장에도 적어뒀다.

**결정:** 목록 보기, 상세 보기, 생성, **상태 변경(transition)**.
그 외(담당자 변경·코멘트 작성·필드 편집)는 여전히 브라우저에서.

**근거:** 사용자가 Jira 웹을 싫어하는 이유는 **느려서**지 기능 부족이 아님.
이 앱의 역할은 "빠르게 보는 것". 편집은 빈도가 낮고, 그때는 느려도 참을 만하다.

**생성이 예외인 이유:** 빈도가 높고 매번 Jira를 여는 게 특히 성가신 작업.

**상태 변경을 넣은 이유:** 생성과 같은 근거다 — **빈도가 높다.** 목록을 보는 것과
같은 자리에서 일어나는 일이라 더 그렇다. "이거 끝났네"는 티켓을 보는 동안 생기는
생각인데, 그때마다 브라우저를 열어 로딩을 기다리는 것이 이 앱을 만든 이유와 정면으로
충돌했다. 조회는 빨라졌는데 그 다음 한 걸음이 여전히 느리면 절반만 해결한 것이다.

#### 11.5.1 원래 우려한 두 가지를 어떻게 풀었나

11.5가 상태 변경을 뺀 근거는 두 개였다. 회피하지 않고 그대로 다뤘다.

**(1) 워크플로우가 프로젝트마다 다르다 → 조회한다. 하드코딩하지 않는다.**

`GET /rest/api/3/issue/{key}/transitions?expand=transitions.fields`로 그 티켓에서
지금 실행할 수 있는 전이만 받는다. 상태 목록을 우리가 아는 척하지 않는다.

실측(2026-08-06)이 이 판단을 지지한다:

| 프로젝트 | 전이 개수 | 비고 |
|---|---|---|
| EDU | 5 | 할 일 / 진행 중 / 검토 중 / 완료 / 백로그 |
| DTH | 7 | + QA / Ready for Release / Released |

개수도 이름도 다르다. 같은 사이트 안에서도 그렇다.

**(2) 전이에 필수 필드가 걸릴 수 있다 → 폼을 만들지 않고 브라우저로 넘긴다.**

이게 이번 결정의 핵심이다. 세 가지 선택지가 있었다:

| 선택 | 결과 |
|---|---|
| 폼을 만든다 | 필드 타입별 렌더러(사용자 검색·날짜·다중 선택…)가 다시 필요하다. 11.3 생성 폼의 범위가 그대로 반복된다 |
| 그 전이를 숨긴다 | "왜 완료 버튼이 없지"가 된다. **조용한 실패**다 (CLAUDE.md 대전제 2) |
| **누르기 전에 말하고 브라우저로 보낸다** | ← 채택 |

**앱에서 못 하는 일을 못 한다고 정직하게 말하면서 다음 행동을 준다.** 그 줄은
실행 버튼이 아니라 "입력 필요" + 외부 링크 아이콘이 붙은 링크가 된다. 눌러서
400을 맞게 두지 않고, **누르기 전에** 알려준다.

판정은 Rust가 한다 — `required: true && hasDefaultValue != true`인 필드가 하나라도
있으면 `has_required_fields: true`. **생성 폼과 똑같은 규칙이다**(11.3, 4.2의 EDU
reporter 사례): `hasDefaultValue: true`는 서버가 채우므로 폼이 필요 없다.
프론트는 이 불리언 하나만 보고 UI를 고른다 — Jira의 필드 스키마를 알 필요가 없다.

`hasDefaultValue`가 응답에서 빠져 있으면 **필수로 본다.** 모르면 안전한 쪽
(브라우저)으로 보낸다. 반대로 가정하면 400을 맞는다.

> **실측 참고:** EDU·DTH의 전이 **전부**가 `fields: {}`였다 — 지금 이 사이트에서
> 브라우저로 넘어가는 전이는 0개다. 그래도 이 경로를 만든 이유는 11.3의
> createmeta와 같다: 설정은 언제든 바뀐다. '완료' 전이에 resolution을 필수로
> 걸어두는 것은 Jira에서 아주 흔한 구성이다.

#### 11.5.2 UI — 목록 행과 상세 모달 둘 다

**공통 컴포넌트 하나**(`widgets/jira/StatusTransitionPopover.tsx`)를 `IssueRow`와
`IssueDetailModal`이 같이 쓴다. 위젯 폴더 안이므로 "위젯 하나 = 폴더 하나"는 그대로다.
두 곳에 같은 팝오버를 따로 두면 한쪽만 고치는 일이 반드시 생긴다.

| 항목 | 결정 | 근거 |
|---|---|---|
| **2단 클릭** | 배지 → 팝오버 → 전이 항목 | **되돌리기가 없는 조작**이다. 목록을 훑다 잘못 누르면 팀 전체에 잘못된 상태가 알려지고, 우리에겐 취소 기능이 없다 |
| **lazy 조회** | 배지를 누른 그 순간 1회 | 행마다 미리 조회하면 티켓 30개에 요청 30개다. 그중 실제로 여는 것은 하나 |
| **캐시** | 메모리 30초. **디스크 캐시 없음** | 전이 가능성은 상태가 바뀌면 **즉시** 낡는다. 방금 완료로 옮긴 티켓에 "완료로 이동"을 보여주는 것보다 조회 한 번이 싸다 |
| **로딩** | 스켈레톤 3줄 | 빈 팝오버는 "고장났나"를 만든다. **펄스는 없다**(DESIGN.md 9장) |
| **전이 성공** | 재조회. **낙관적 업데이트 없음** | 도달 상태는 알지만 워크플로우 후처리(자동 담당자 변경 등)는 예측할 수 없다. 우리가 그린 값이 서버와 다를 수 있다 |
| **전이 실패** | **팝오버 안에 인라인** | 전역 배너가 아니다 — **어느 티켓이 실패했는지가 정보다**(DESIGN.md 5.1의 판단 기준: 다른 위젯에도 똑같이 날 에러인가? 아니다) |
| **전이 0개** | "가능한 전이가 없습니다" + 브라우저 링크 | 빈 배열은 **에러가 아니다.** 권한이 없거나 워크플로우 끝단이다 |

배지 클릭은 `stopPropagation`한다. 행 전체 클릭이 이미 상세 모달을 열기 때문에
(11.4 D1) 안 막으면 팝오버와 모달이 동시에 열린다. 테스트로 고정해뒀다 —
같은 함정을 티켓 키 링크에서 이미 한 번 밟았다.

팝오버는 **포털로 body에 붙인다.** 위젯 안에서 렌더하면 위젯의 `overflow-hidden`과
목록 스크롤 컨테이너에 잘린다. `position: fixed`도 안 되는데, react-grid-layout이
조상에 `transform`을 걸어두면 fixed의 기준이 뷰포트가 아니게 된다 — 모달이 같은
이유로 이미 포털이다.

#### 11.5.3 자동 재시도를 하지 않는다

전이는 **멱등이 아니다.** 같은 요청이 두 번 나가면 워크플로우를 두 칸 움직일 수
있고(할 일 → 진행 중 → 검토 중), 우리에겐 되돌리는 기능이 없다. 생성이 400만
재시도하는 것과 같은 이유이며(11.3), 여기서는 그 400조차 재시도하지 않는다 —
400이면 필수 필드가 걸렸다는 뜻이고 그건 폼 없이 채울 수 없다.

재시도 판단은 사람이 팝오버에서 한다. 일시적 실패(429/5xx)에만 [다시 시도]를
그린다. 403·404에 재시도 버튼을 주면 몇 번을 눌러도 같은 결과인 버튼을 주는 셈이다.

성공 응답은 **204 No Content**다. 본문 파싱 경로를 그대로 쓰면 빈 본문에서
`Decode` 에러가 나서 **성공한 전이를 실패로 보고한다.** 상태코드만 본다.

## 12. GitHub 위젯

**결정:** 위젯 타입 **하나**. 쿼리 기반. PR/Issue 통합.

**근거:** GitHub에서 PR은 이슈의 특수 형태. 검색이 `is:pr` / `is:issue`로 구분.
GitHub 검색 문법이 JQL 역할을 그대로 함 → Jira 위젯과 구조 일관성.

**프리셋 5종 (2026-08-02 구현, 괄호는 실측 건수):**

| id | 검색 | 건수 |
|---|---|---|
| `involves-me` **기본** | `involves:@me is:open` | 13 |
| `review-requested` | `is:pr is:open review-requested:@me` | **0** |
| `my-prs` | `is:pr is:open author:@me` | 3 |
| `assigned-issues` | `is:issue is:open assignee:@me` | 2 |
| `my-issues` | `is:issue is:open author:@me` | 9 |

계획에 없던 `involves-me`를 넣고 **기본값으로 삼았다.** Jira의 "최근 내가 관련된
티켓"에 대응하는 자리인데 원래 4종에 없었고, 실측에서 가장 건수가 많다.
위젯을 처음 놓았을 때 빈 화면이면 고장으로 보이므로 기본값은 뭐라도 나오는
쪽이어야 한다.

`review-requested`는 0건이지만 **남긴다.** 회사 저장소가 붙으면 채워질 자리이고,
놓치면 안 되는 것이라 목록에 없으면 존재를 잊는다. 다만 기본값으로는 쓰지 않는다.

모든 프리셋에 `is:open`을 박았다. 닫힌 것까지 섞이면 "지금 볼 것"이 흐려진다.
닫힌 것을 봐야 하면 직접 입력으로 간다.

**PR/Issue를 안 나눈 이유:** PR 고유 정보(리뷰 상태·CI)는 **표시 차원에서 해결**.
항목이 PR이면 뱃지를 추가로 그리면 됨. 타입을 나눌 만큼의 차이가 아님.

**저장소 중심 위젯을 거부한 이유:** 저장소가 여러 개면 위젯 폭증.
사용자가 원하는 건 "저장소 무관하게 내가 볼 것들".

### 12.2 목록 — 고정 2행. 열 설정 없음

```
⇅ feat: 로비 세리머니 동상 2개 + 이동 범위 확장
  my-gallery #1 · 승인 · CI · +1149 −29 · 2일 전
```

**열 설정을 두지 않는다.** Jira에 그것이 필요했던 이유는 **프로젝트마다 필드가
달라서**였다(라벨·컴포넌트 채움률 0/22가 그 증거). GitHub은 반대다 — 필드가
고정이고 전부 의미가 있다. 고를 이유가 없는데 설정을 만들면 안 쓰는 UI만 는다.

특히 **리뷰 상태와 CI는 항상 보여야 한다.** 이걸 끌 수 있게 만들면 GraphQL을
택한 이유(12.1 — "하나씩 열어봐야 하면 위젯의 의미가 반감")가 무너진다.

**Jira는 1행 밀집인데 여기는 2행인 이유:** GitHub 제목이 훨씬 길다. 실측에서
"feat: 설치형 앱 창으로 띄울 수 있도록 PWA 지원 추가" 같은 것이 나온다.
제목을 메타데이터와 한 줄에 두면 둘 다 잘린다.

종류(PR/Issue)와 상태는 **아이콘 하나**로 합쳤다. 따로 그리면 좁은 폭에서
자리를 두 배로 먹고, GitHub 자체가 쓰는 관례라 학습 비용도 없다.
머지는 초록이 아니라 **보라**다(`--color-merged`) — "잘 끝났다"와 "합쳐졌다"는
다른 사실이고 GitHub 사용자는 보라를 머지로 읽는다.

### 12.3 저장소 — 필터와 순서는 다른 기능이다

**필터**(범위 좁히기)와 **그룹 순서**는 서로 다른 설정이다. 섞으면 사고가 난다.

**그룹핑은 기본 켬.** 그룹 순서는 **사용자 지정 먼저 → 나머지는 최신순**이다.
최신순인 이유: "지금 뭐가 움직였나"가 이 앱의 목적이라, 이름순이나 개수순으로
두면 오래된 저장소가 위에 눌러앉아 최신 항목이 아래로 밀린다.

> **지정하지 않은 저장소도 반드시 보인다.** 순서 목록을 필터로 겸하면
> 리뷰 요청이 온 저장소를 등록해두지 않았다는 이유로 **조용히 사라진다** —
> CLAUDE.md 대전제 2와 정면으로 부딪친다. 범위를 좁히려면 필터를 쓴다.

**실측이 그룹핑을 반대했지만 켜기로 했다.** 표본(13건/9저장소)에서 8개
저장소가 1건씩이라 헤더 9개가 항목 13개를 나르는 꼴이었다. 그럼에도 기본으로
켠 것은 사용자 판단이다 — 회사 저장소가 붙으면 분포가 달라질 여지가 있고,
끄는 것은 체크박스 하나다. 실사용에서 성기게 느껴지면 기본값을 뒤집는다.

**저장소 목록은 `github_meta.json`에 캐시**한다(실측 68개). `jira_meta.rs`와
같은 이유로 `cache/`가 아닌 별도 파일이다 — `board_save`의 orphan 정리가
위젯 id 없는 파일을 지운다. 정렬은 최근 푸시순이고, 아카이브된 저장소는
목록에서 버리되 이미 필터에 든 것은 남긴다.

### 12.4 인증 — 앱 자체 토큰 + gh CLI 가져오기

**결정:** 토큰을 키체인(`github.default.token`)에 저장한다. 설정창의
**"gh CLI에서 가져오기"** 버튼이 `gh auth token`을 한 번 실행해 그 값을
**복사**한다.

**gh를 런타임 의존으로 삼지 않은 이유가 셋이다.**

1. **조용한 실패의 온상이다.** gh 로그아웃·재설치·토큰 만료·PATH에 없음 —
   전부 앱 밖에서 일어나고 앱은 "왜 안 되지"만 겪는다
2. `gho_`는 OAuth 토큰이라 **gh가 소유권을 갖는다.** 재로그인 때 바뀌는데
   매번 서브프로세스를 띄워 읽으면 시작 비용 + 출력 파싱 리스크가 붙는다
3. **배포하면 무너진다.** dmg를 남에게 주는 순간 "gh부터 설치하세요"가 된다

복사해두면 gh가 사라져도 앱이 돈다. 대가는 gh가 토큰을 갱신했을 때 우리 사본이
낡는 것인데, 그때는 401이 나고 버튼을 다시 누르면 된다 — **드러나는 실패**다.

> **조직 SSO.** 조직이 SAML SSO를 걸어두면 토큰을 따로 authorize해야 하고,
> 그 전까지 해당 조직 저장소가 목록에서 **빠진다**(403도 아니고 그냥 안 온다).
> 빈 목록만 보여주면 원인을 알 수 없으므로 설정창과 위젯 설정 양쪽에
> "SSO 인증이 필요할 수 있습니다" 안내를 상시 노출한다.

### 12.5 상세보기 — 만들지 않는다

**결정:** 항목을 누르면 브라우저로 나간다. 상세 모달이 없다.

Jira에 상세를 만든 이유는 **회사 Jira 웹이 느려서**였다. GitHub 웹은 그 전제가
성립하지 않는다. 그리고 PR 본문은 GitHub Flavored Markdown이라 ADF 렌더러를
재사용할 수 없고 렌더러를 하나 더 만들어야 한다.

목록이 리뷰 상태·CI·변경 규모를 이미 보여주므로 "열어볼지 말지"를 판단하는 데
충분하다. 그게 GraphQL을 택한 이유이기도 하다.

### 12.1 API — GraphQL

**결정:** GitHub GraphQL API. REST 검색 API 미사용. **github.com 전용** (Enterprise 미지원).

**결정적 근거 — rate limit:**
- REST 검색: **분당 30회**. PR 30건의 리뷰 상태를 개별 조회하면 즉시 초과
- GraphQL: 포인트 기반(시간당 5000점, 일반 쿼리 1~10점). 한 요청으로
  `search(query:..., type:ISSUE, first:30)` + 각 PR의 `reviewDecision`·`statusCheckRollup`·`additions/deletions`

**왜 중요한가:** "리뷰 요청 3건" 목록에서 승인 여부·CI 상태를 모르면 결국 하나씩 열어봐야 함
→ 위젯의 의미가 반감.

**대가:** GraphQL 쿼리를 Rust 문자열로 관리, 응답 파싱 struct 중첩이 깊음.
→ 그 대가는 **실제 응답 fixture 테스트**로 갚는다. 문자열 상수라 오타가
컴파일에 안 잡히므로, `gh api graphql`로 캡처한 진짜 응답을 파싱해본다.

**실측으로 확인한 것 (2026-08-02):**

| 항목 | 값 |
|---|---|
| 검색 1회 비용 | **1점** (한도 5000점/시간) |
| 위젯 4개 × 5분 주기 | 시간당 48점 = 한도의 **1%** |

rate limit은 사실상 제약이 아니다. 그래서 폴링 주기는 rate limit이 아니라
**체감**으로 정했다 — Jira와 같은 300초.

문서와 달랐던 것 셋:

- **`statusCheckRollup`은 최상위 필드가 아니다.** `commits(last: 1).nodes[0].commit`
  아래에 있다. 경로가 틀리면 조용히 `None`이 된다
- **`reviewDecision`은 리뷰어 미지정 시 `null`**이다. "리뷰 대기"가 아니라 없음
- **검색이 총 건수를 준다**(`issueCount`). 신규 Jira 검색은 total이 없어서
  "42건 중 30건"을 만들 수 없었는데(11장 ⚠️), GitHub은 가능하다

**에러 분류에 Jira에 없는 축이 둘 있다:**

- **GraphQL은 실패해도 200을 준다.** 본문의 `errors` 배열을 봐야 한다.
  상태 코드만 보면 전부 성공으로 보인다
- **403이 rate limit일 수 있다.** GitHub은 429 대신 403을 쓰기도 하고,
  `x-ratelimit-remaining: 0`이 유일한 단서다. 이걸 안 보면 **SSO 미인증
  403을 재시도하며 시간을 버린다**

## 13. Todo 위젯 — 날짜별 daily todo

**결정:** 단순 체크리스트가 아니라 **날짜 축을 가진 daily todo + 자동 이월**.

**데이터 구조:**
```
{ id, text, done, date: "2026-07-29", originDate: "2026-07-27", carriedCount: 2 }
```
- `date`: 현재 놓인 날짜
- `originDate`: 최초 생성 날짜
- `carriedCount`: 이월 횟수

**이월 규칙:**
- **시점:** 앱 시작 시 + 자정 넘김 시. **과거 편집 중에는 실행하지 않음**
  (눈앞에서 항목이 튀어나가면 혼란). 다음 실행 때 정리됨
- **범위:** 어제만이 아니라 **과거 전체**. 주말에 앱을 안 켰으면 금요일 항목도 월요일로
- **방식:** 복사가 아니라 **이동**. 항목은 하나만 존재하고 `date`만 바뀜
  - 복사하면 과거에 미완료 유령이 영원히 남아 "어제 뭐 했지"를 볼 때 노이즈
  - 대가: 과거를 다시 쓰게 됨. 7/27로 돌아가도 그날 못 끝낸 항목은 안 보임
  - 수용 근거: daily todo의 목적은 기록 보존이 아니라 **오늘 할 일을 정확히 아는 것**
- **자동 실행.** 되돌리기는 두지 않는다 (2026-08-03).
  이월은 **이동**이라 되돌릴 일이 적고, 자동 이월 자체를 끌 수 있게 되면서
  "원치 않는 이월"이라는 상황이 사라졌다. `TodoStore::undo_carry_over`는
  코드에 남아 있지만 커맨드로 노출하지 않는다.
- **자동 이월은 위젯 설정에서 끌 수 있다.** 끄면 과거에 그대로 남고,
  위젯 헤더의 ↓ 버튼으로 필요할 때만 가져온다. 버튼은 가져올 것이 있을 때만
  보이고, hover하면 무엇이 딸려오는지 목록으로 알려준다 — 누르기 전에
  무엇이 튀어나올지 알아야 한다.

**표시:** 이월 항목은 `↻` 아이콘 + `N일째` 배지. 횟수가 늘수록 색이 진해짐.
미루고 있다는 걸 시각적으로 압박하는 것이 이 기능의 요점.

**날짜 전환:** 헤더에 `◀ 7월 29일 (오늘) ▶`
- 과거: **편집 가능** (체크 누락 수정 등)
- 미래: **추가 가능** ("내일 이거 해야지")

**좀비 항목:** `carriedCount >= 7`이면 "이거 정말 할 건가요?" 힌트. **자동 삭제 절대 안 함.**

**완료 항목:** 취소선 + 흐리게 + **구분선 아래로**. 자동 삭제 없음.

> **2026-08-01 — "완료 항목 정리"(삭제)를 없앴다.**
>
> 이월이 **이동**이므로 완료 항목은 그날에 남는 유일한 것이고, 곧 **그날의 기록**이다.
> 과거 날짜를 열면 대개 완료 항목만 보인다 — "어제 뭐 했지"의 근거가 그것이다.
> 그런데 "정리"는 바로 그 기록을 지우는 버튼이라 목적과 충돌한다.
> 개별 삭제(`×`)는 그대로 있다.
>
> **2026-08-03 — 접기도 없앴다. 그냥 구분선 아래에 둔다.**
>
> 접기는 상태(펼침/접힘)와 조작을 하나 더 만드는데, 하루 항목 수가 십여 개
> 수준이라 그 비용을 낼 만큼 시야를 가리지 않는다. 개수 문구("완료 3개")도
> 뺐다 — 항목이 이미 보이는데 세어서 말할 이유가 없다.

**순서 변경 — 드래그. 끄는 주체는 손잡이다 (2026-08-02).**

미완료 항목만 끌 수 있다. 완료 항목은 구분선 아래에 있어서 섞으면 "완료를
미완료 사이로" 같은 무의미한 이동이 된다. 순서는 `todos.json`의 배열 순서
그대로이고, 날짜 안에서만 움직인다 — 날짜를 넘기는 이동은 이월의 일이다.

**행이 아니라 `<span>` 손잡이에 `draggable`을 건다.** 이유가 두 겹이다.

먼저 행 전체를 끌 수 있게 두면 텍스트를 집으려다 행이 딸려오고, 체크박스를
누르려다 드래그가 걸린다. 그래서 손잡이가 필요하다.

문제는 그 다음이다. "손잡이를 누를 때만 행의 `draggable`을 켠다"는 방식은
**두 번 실패했다.**

| 시도 | 왜 실패했나 |
|---|---|
| state로 켜기 | 리렌더가 `pointerdown`보다 늦다. 브라우저는 `pointerdown` 시점에 draggable 여부를 이미 정한다 |
| ref로 DOM 직접 켜기 | 순서를 바꾸면 React가 `<li>`들을 **옮겨서** 재조정한다. 뒤이어 온 `dragend`의 해제가 엉뚱한 행에 적용되어, 끌었던 행은 켜진 채 남는다 |

두 번째가 특히 고약했다 — 증상이 "한 번 옮기면 다음 손잡이가 안 잡히고,
헛클릭을 한 번 해야 잡힌다"였다. 그 헛클릭이 정착된 DOM에 값을 다시 써주는
것이었다.

**손잡이를 항상 `draggable`로 두면 켜고 끌 일이 없다.** 브라우저가 늘 같은
답을 알고 있으므로 타이밍도 재조정도 끼어들 여지가 없다. 편집 중에는 속성을
끄는 대신 **손잡이를 아예 그리지 않는다.**

곁들여 필요한 것 둘:
- `setDragImage`로 **행 전체**를 캡처한다. 안 하면 12px 손잡이만 따라다닌다
- 그 호출을 가드한다. `dragstart`에서 예외가 나면 드래그가 통째로 죽는다

**끌리는 행은 자리를 지킨다.** `h-0`으로 접었더니 돌아올 자리가 사라져 제자리
드롭이 불가능했다. 자리를 두되 `opacity-25`로 죽여 "여기서 빠져나갔다"를 보인다.
드롭 표시선은 대상의 **위/아래를 구분**해 긋는다 — 아래로 끌 때도 선이 위에만
뜨면 한 칸 어긋나 보인다. 원래 자리 위에서도 선을 보여준다(제자리 드롭 표시).

> **Tauri 함정:** `dragDropEnabled`가 기본 `true`라 OS 레벨에서 드래그를
> 가로챈다. 웹 쪽을 아무리 고쳐도 `+` 포인터만 뜨고 아무 일도 안 일어난다.
> `tauri.conf.json`에서 꺼야 한다. 이걸 못 찾아 **네 번 헛짚었다.**

**날짜 소유권:** 보고 있는 날짜는 **세션 상태**다. board.json에 저장하지 않는다 —
어제 만든 보드를 오늘 열었을 때 어제를 보고 있으면 안 된다. 재시작하면 오늘로 돌아온다.

**배지 숫자:** `originDate` 기준 **경과일**이다(`carriedCount`가 아니다).
금요일에 만들어 월요일에 이월되면 이월은 1회지만 3일이 지났다 — "1일째"는 거짓말이다.
다만 **색과 좀비 판정은 `carriedCount` 기준**을 유지한다. 둘은 다른 것을 잰다:
"얼마나 오래됐나"와 "몇 번이나 미뤘나". 주말에 안 한 것을 미룬 것으로 치지 않는 게 공정하다.

**자정 감지:** 1분마다 날짜 문자열이 바뀌었는지 확인한다. `setTimeout`은 macOS
잠자기에서 멈춰서 노트북을 덮고 다음 날 열면 안 깬다. 폴링은 잠자기·시간대 변경·
수동 시계 조정에 전부 견딘다.

**Jira/GitHub 연동을 거부한 이유:** 티켓을 todo로 복사하면 두 곳에서 상태를 관리하게 되고 반드시 어긋남.

**저장:** `todos.json` 하나에 전체. 날짜별 파일 분리 안 함 (이월 로직이 여러 파일을 건드리지 않도록).

## 14. 보드 — 다중 보드 탭 (2026-08-06 개정)

**결정:** 보드를 여러 개 만들 수 있다. 타이틀바에 탭으로 노출한다.

> **이 장은 개정되었다.** 원래는 "보드 1개, 다중 보드 UI 없음"이었다.
> **전제는 뒤집히지 않았고 근거가 교체됐다.** 아래 14.1이 그 구분을 다룬다.

### 14.1 무엇이 바뀌었고 무엇이 안 바뀌었나

**안 바뀐 것 — 원래의 전제는 여전히 참이다.**
"실제 위젯 수가 5~7개면 화면 하나에 다 들어간다"는 맞다. 지금도 맞다.
그래서 **보드당 위젯은 적게 유지하는 것이 옳다.**

**바뀐 것 — 근거가 교체됐다.**
원래 근거는 **위젯 수**였다: "다 보이는데 왜 나누나."
새 근거는 **맥락 전환**이다: **지금 볼 것이 상황마다 다르다.**

업무 중일 때 보고 싶은 것과 개인 시간에 보고 싶은 것은 겹치지 않는다.
한 화면에 다 올릴 수 있느냐를 묻는 게 아니라, **지금 안 볼 것이 시야에 있느냐**를
묻는 것이다. 이건 면적 문제가 아니라 주의(attention) 문제라서 위젯 수로 답할 수 없다.

> 원래 결정이 틀렸던 지점은 **"탭"이라는 수단만 보고 목적을 하나로 가정한 것**이다.
> 탭의 목적이 "위젯을 더 담기"라면 원래 판단이 맞다. 목적이 "지금 안 볼 것을
> 치우기"면 반대다. 같은 UI가 정반대의 결정을 받는다.

**따라서 보드를 늘려 위젯을 더 담으려는 것이 아니다.**
`maxInstances`는 **보드당**으로 센다 (Jira 4 / GitHub 4 / Todo 1 / Web 4 / 앨범 4).
전체 상한이 아니다 — 맥락 전환이 목적이면 보드마다 그 맥락의 위젯이 필요하다.
구현상 추가한 코드가 0줄이다. `addWidget`이 원래부터 `board.widgets`를 셌다.

### 14.2 원래 경고는 살아 있다 — 그리고 완화 장치가 필요하다

원래 결정의 경고문은 폐기되지 않았다:

> "탭 뒤에 숨은 위젯은 안 보게 되고, 안 보는 위젯은 없는 것과 같다."

이건 지금도 사실이다. 탭을 추가한 것은 이 문제가 없어졌다는 뜻이 아니라
**맥락 전환의 이득이 이 비용보다 크다**고 판단한 것이다. 비용은 남아 있으므로
줄여야 한다.

**완화 장치: 탭에 그 보드의 위젯 수를 표시한다.**
비활성 탭도 자기가 무엇을 들고 있는지 말한다 — `업무 3` / `개인 2`.
숫자가 있으면 "저쪽에 3개가 있다"는 사실이 시야에 남는다. 잊는 것은
"안 보인다"에서 오지, "다른 화면에 있다"에서 오지 않는다.

**표시하지 않기로 한 것: 에러·갱신 상태 배지.**
탐나는 기능이지만 **만들 수 없다.** 비활성 보드는 렌더되지 않아 폴링하지
않으므로(14.3) 그 보드의 위젯이 지금 성공인지 실패인지 **알 수 없다.**
모르는 것을 표시하면 거짓말이 된다 — 30분 전 상태를 지금 상태처럼 보여주거나,
아예 물어보려고 비활성 보드까지 폴링하면 14.3을 스스로 무너뜨린다.

> **위젯 수는 보드 데이터만으로 정확히 아는 유일한 정보다.** `board.json`에
> 적혀 있으므로 조회도, 추측도 필요 없다. 그래서 이것만 표시한다.
> 대전제 2("실패는 화면에 드러나야 한다")는 **아는 실패**를 숨기지 말라는
> 규칙이고, 모르는 것을 지어내라는 규칙이 아니다.

### 14.3 전환 시 동작 — 캐시 즉시 + 뒤에서 갱신

**탭을 누르면 0ms에 지난 데이터가 보이고, 그 뒤에 조용히 갱신된다.**
앱 시작과 똑같은 모양이다 (CLAUDE.md 대전제 1). 스피너로 시작하지 않는다.
**탭 전환이 병목이 되면 탭은 실패한 기능이다** — 속도가 기능보다 우선한다.

**구현: 비활성 보드는 렌더하지 않는다(언마운트).**
공짜로 따라오는 것이 두 개다:
- 데이터 훅이 마운트 시 **1단계 캐시 즉시 그리기 → 2단계 네트워크**를 한다
  (`useJiraData.ts` / `useGithubData.ts`) → 캐시-즉시-표시가 자동
- 훅이 언마운트에서 `clearInterval` 한다 → **폴링 중단이 자동**

**비활성 보드를 숨긴 채 마운트해두지 말 것.** `display:none`으로 감추면
안 보는 보드가 계속 API를 때리고 메모리도 잡는다. 화면에 드러나지 않는
실패라서 `BoardTabs.test.tsx`의 "비활성 보드는 마운트되지 않는다"가
이걸 고정한다.

> **원래 결정의 세 번째 조치는 틀린 예측이었다.** 원문은
> "Rust 스케줄러가 위젯을 보드 단위로 그룹핑 → 비활성 보드 폴링 중단이
> 한 줄로 들어감"이라고 적었다. **그런 스케줄러는 만들어지지 않았다** —
> `scheduler/` 디렉터리가 없고 폴링은 데이터 훅 안의 `setInterval`이다.
> 결과적으로 폴링 중단은 한 줄도 아니라 **0줄**이었다. React 언마운트가
> 이미 하고 있었다. 미리 깔아둔 대비책이 쓰이지 않았고, 실제로 값을 한 것은
> 아래 두 개다.

**실제로 값을 한 대비:**
- `board.json`이 처음부터 `boards: []` 배열 → **스키마 버전을 올리지 않았다.**
  파일 형식이 바뀌지 않으므로 구버전 파일이 그대로 읽힌다 (보드 1개 = 탭 1개)
- 상태 접근이 `useActiveBoard()` 하나뿐 → **위젯 쪽 코드를 한 줄도 안 고쳤다**

### 14.4 UI — 타이틀바 안, 탭 1개면 숨김

**탭 바는 타이틀바(h-9) 안에 있다.** 보드 영역을 한 픽셀도 쓰지 않는다.
대시보드의 가치는 화면 면적이고, 위젯 위에 탭 줄을 한 개 얹으면 매일 그만큼을
낸다. 타이틀바는 창을 끌기 위해 **어차피 비어 있던 공간**이다
(macOS Overlay + `hiddenTitle`). 좌측 `pl-20`은 신호등 버튼 자리다.

**탭이 1개면 탭 바를 아예 그리지 않는다.**
지금 사용자는 보드 1개다. 쓰지 않는 기능이 화면을 차지하면 원래 결정의
우려("안 보는 것이 자리를 먹는다")가 다른 형태로 실현된다. 보드가 2개가 되는
순간 나타나고, 1개로 돌아가면 사라진다.
→ 그래서 "보드 추가"가 두 곳에 있다: 탭 바 안의 `✚`(2개 이상일 때), 그리고
타이틀바의 "보드 추가" 버튼(1개일 때만 보임). 없으면 첫 보드를 만들 길이 없다.

**단축키 `⌘1`~`⌘9`.** 브라우저·에디터의 탭 전환 관례를 그대로 쓴다.
기존 단축키(`⌘,` `⌘R` `⌘N` `⌘⇧N`)와 겹치지 않는다 — 숫자를 쓰는 것이 하나도
없었다. `⇧`를 안 누른 경우만 받는다(`⌘⇧숫자`는 입력기가 가져가는 경우가 있다).
그 자리에 보드가 없으면 `preventDefault`도 하지 않는다.

`role="tablist"` / `role="tab"`, `←` `→`로 이동, 활성 탭만 `tabIndex=0`
(tablist 관례 — Tab 키 한 번에 탭 그룹을 지나간다).

### 14.5 CRUD

| 동작 | 방식 |
|---|---|
| 생성 | `✚` → 새 보드로 즉시 전환. 이름은 `보드 2`, `보드 3` … 중 **비어 있는 첫 번호** |
| 이름 변경 | `✎` · 더블클릭 · **F2** → 인라인 편집. Enter 확정 / ESC 되돌림 / 빈 이름 거부 |
| 삭제 | `✕` → 확인창 (활성 탭은 상시, 나머지는 호버). **마지막 보드는 못 지운다** |
| 순서 변경 | 탭 드래그 |
| 전환 | 클릭 / `←` `→` / `⌘1`~`⌘9` |

**새 이름을 "개수 + 1"로 짓지 않는다.** `보드 2`를 지우고 다시 추가하면
`보드 3`이 되어 이미 있는 탭과 이름이 같아진다. 이름이 같은 탭은 어느 쪽을
눌러야 하는지 알 수 없다.

**삭제는 되돌릴 수 없고, 사라지는 것은 탭 하나가 아니라 그 안의 위젯 설정
전부다.** 그래서 확인창이 **숫자로 말한다**: "위젯 3개가 함께 삭제됩니다.
되돌릴 수 없습니다." 위젯 삭제 확인창과 같은 원칙이다 — 무엇을 잃는지 밝히지
않는 "정말요?"는 반사적으로 눌려서 아무것도 막지 못한다.

**✕는 활성 탭에 상시, 나머지 탭에는 호버·포커스했을 때 보인다.**

처음에는 활성 탭에만 그렸다. 근거는 "모든 탭에 상시로 보이면 옆 탭을 누르려다
`✕`를 누른다"였고 그 우려 자체는 유효하다. 다만 그렇게 두면 **지우려는 보드에
일단 들어가야** 해서, 안 쓰는 보드를 정리하려면 그 보드를 활성화하고(위젯이
전부 마운트되고 폴링이 돌기 시작한다) 지우는 순서가 된다.

오조작은 배치로 막는다:

1. **✕는 자리를 늘 차지한다.** 조건부 렌더가 아니라 `invisible` ↔ `visible`이다.
   나타나면서 탭들이 밀리면 누르려던 탭이 커서 밑에서 움직인다 — 오클릭의
   가장 큰 원인이 그것이다
2. **✕는 탭 버튼 바깥의 형제다.** 탭의 클릭 영역을 덮지 않으므로 탭 가운데를
   누르면 늘 전환이고, `✕`는 자기 20px만 갖는다
3. 확인창은 그대로다. 되돌릴 수 없는 동작에서 마지막 방어선을 없애지 않는다

비활성 탭의 `✕`는 `tabIndex={-1}`이다. 호버로 드러나는 버튼을 탭 순서에 넣으면
보이지 않는 것에 포커스가 가고, 화살표로 탭을 옮기면 활성이 되어 도달할 수 있다.

**`✎`도 같은 규칙을 쓴다.** 이름 변경은 되돌릴 수 있어서(다시 바꾸면 된다)
`✕`보다 오조작 위험이 낮지만, 두 버튼이 나란히 있으므로 규칙이 다르면
탭 폭이 **두 단계로** 변한다 — 그 사이에서 커서가 노리던 버튼이 밀린다.
`✎`가 있는 이유는 더블클릭·F2가 둘 다 **보이지 않는 조작**이라는 것이다.
그것만 두면 "이름을 바꿀 수 있다"는 사실 자체를 모른다.

**마지막 보드는 UI가 막는다.** Rust의 `BoardStore::load`가 빈 `boards`를
기본 보드로 복구하지만 그건 **손으로 파일을 고친 경우의 방어선**이다.
방어선에 정상 경로를 의존시키지 않는다.

**삭제 후 활성 보드:** 지운 보드를 보고 있었으면 **그 자리의 오른쪽**,
없으면 왼쪽으로 옮긴다. `activeBoardId`를 없는 보드에 남기면 `useActiveBoard`가
조용히 첫 보드로 폴백해서 "왜 이 보드가 열렸지"가 된다.

### 14.6 저장

보드 추가·이름 변경·삭제·순서 변경·**전환**이 전부 `board.json`에 반영된다.
기존 디바운스 경로(`store/persist.ts`, 500ms)를 그대로 쓴다.

**`activeBoardId`도 저장한다.** 앱을 다시 켜면 마지막에 보던 보드가 열려야 한다.
→ `persist.ts`의 구독 조건이 원래 `state.boards !== prev.boards`뿐이었다.
탭 전환은 `boards` 배열을 건드리지 않으므로 **그대로 두면 저장되지 않는다** —
"탭을 옮겨두고 재시작했는데 첫 보드가 뜬다"는 조용한 실패다. 조건에
`activeBoardId` 비교를 추가했다.

**스키마 버전은 올리지 않았다.** 구조가 이미 다중 보드였으므로 파일 형식이
바뀌지 않는다. 마이그레이션이 없고, 구버전 파일이 보드 1개 = 탭 1개로 읽힌다.

## 15. 설정창 — 전체 모달, 탭 2개, 연결 1개

**형태:** Tauri 별도 창이 아닌 **전체 화면 모달**.
별도 창은 위치 기억·중복 방지·포커스 관리 상태가 늘지만 얻는 게 없음.

**탭 2개: `연결` / `정보`** (2026-08-06 개편)

| 탭 | 내용 |
|---|---|
| 연결 | Jira 연결 · GitHub 연결 |
| 정보 | 앱 아이콘·이름·버전 · 업데이트 확인/설치 · GitHub 링크 · 라이선스 |

**왜 탭인가:** 연결은 한 번 넣고 안 건드리는 것이고, 정보(버전·업데이트)는 자주 보는
것이다. 한 스크롤에 쌓으면 자주 보는 쪽이 아래로 밀린다. 스크롤 순서를 뒤집으면
설정을 열 때마다 버전 숫자가 먼저 보이는데 그것도 이상하다. 탭이 이 긴장을 없앤다.

**왜 사이드바가 아닌가:** 항목 2개에 좌측 150px을 상시 내주고 얻는 게 없다.

**왜 Jira/GitHub를 각각의 탭으로 쪼개지 않나:** 둘 다 "토큰 넣기" 한 덩어리이고
합쳐도 화면 하나에 들어간다. 쪼개면 "GitHub 토큰 넣으려면 탭 이동"이 되어 클릭만
는다. 연결이 4~5개로 늘면 그때 쪼갠다.

**왜 `일반` 탭을 미리 만들지 않았나:** 넣을 앱 전역 설정이 **현재 0개**다.
`refreshSecs`는 위젯별로 각자 갖고 있고(위젯 설정에 이미 노출), 테마는 다크 고정이다.
빈 탭은 "여긴 뭐가 있어야 하는데 없다"는 인상을 준다 — 미완성으로 보인다.
탭 추가 비용은 배열 한 줄이므로 내용이 생기는 시점에 만든다.

**기본 탭은 `연결`.** 마지막 탭을 기억하지 않는다 — 어제 정보 탭을 봤다고 오늘
설정을 열었을 때 정보가 뜨면 당황스럽고, 상태를 하나 더 저장해야 한다.
**단 업데이트 배지가 켜져 있으면 `정보` 탭으로 연다** (23장).

**정보 탭에 메모리·폴링 소요 시간이 아직 없다.** CLAUDE.md가 약속한 항목이지만
성능 계측은 주제가 다른 작업이고(Rust 신규 작업 2덩이 + 의존성), 지금 없어서 겪는
불편이 없다. `commands::app_info`가 `memory_bytes: None`으로 자리를 잡아두고 있다.

**경계:**
| 위젯 설정 (톱니바퀴) | 앱 설정 (통합 설정창) |
|---|---|
| 제목, 쿼리, 표시 개수, 새로고침 주기, 표시 필드 | 계정/토큰, 테마, 시작 동작, 데이터 관리 |

**연결은 서비스당 1개.** 다중 연결 UI 없음.
**단, 구조는 대비:** Keychain 키 `jira.default.token`, 위젯 config에 `connectionId: "default"`.

**다중 연결을 안 만든 이유:** 모든 위젯 설정에 "연결 선택" 드롭다운이 추가되고,
연결 삭제 시 그걸 쓰던 위젯 처리가 필요. 쓰지 않을 유연성에 매번 클릭 하나씩을 내는 셈.

## 16. 에러 처리 — 일시적/영구적 분리

**이것은 부가 기능이 아니라 핵심 기능.** 콘솔에만 남는 실패는 사용자에게 없는 것과 같다.

| 실패 | 성격 | 처리 |
|---|---|---|
| 401 토큰 만료 | 영구 | 전역 배너 + 알림 + [설정 열기] |
| 403 권한 없음 | 영구 | 위젯 에러 상태 |
| 400 JQL 오류 | 영구 | Jira 원문 메시지 그대로 (Jira 메시지가 친절함) |
| 429 rate limit | 일시 | 백오프 재시도 |
| 네트워크 끊김 | 일시 | 백오프 재시도 |
| 5xx | 일시 | 백오프 재시도 |

**일시적 실패:** 지수 백오프 3회. **재시도 중 직전 성공 데이터를 계속 표시** + "5분 전 데이터" 흐린 표시.
목록이 사라지면 안 됨. 3회 실패 시 하단에 얇은 경고 줄. 다음 폴링에 복구되면 경고도 사라짐.

**영구적 실패:** 재시도 없음. 위젯 본문을 에러 상태로 교체 + **무엇을 해야 하는지** + 행동 버튼.

**전역 실패:** 토큰 만료 시 그 서비스의 모든 위젯이 동시에 깨짐 → 같은 에러 4번은 소음.
**인증 실패는 앱 상단 배너 한 번만**, 위젯들은 조용히 흐려짐.

**로그:** `~/Library/Logs/io.mypegboard.app/` 회전 로그. **토큰 마스킹 필수.**
"어젯밤 뭔가 실패했는데 지금은 정상"을 나중에 추적할 유일한 수단.

**알림:** 인증 실패만. 나머지는 화면 안에서.

## 17. 성능 목표 (측정 가능한 기준)

**형용사가 아닌 숫자로.** "최적화했다"는 주장은 측정값으로만 검증된다.

| 항목 | 목표 |
|---|---|
| 앱 시작 → 보드 표시 | 1초 이내 |
| **캐시된 데이터 표시** | **즉시 (0ms)** |
| 위젯 새로고침 체감 | 1초 이내 |
| 유휴 메모리 (전체) | 150MB 이하 |
| 위젯 드래그 | 60fps |
| 모달 열기 | 100ms 이내 |

**가장 중요한 건 두 번째 줄.**
> "앱을 켜면 즉시 지난 데이터가 보이고, 그 뒤에 조용히 갱신된다."

이것이 Jira 웹과의 결정적 차이. Jira 웹은 열 때마다 빈 화면에서 로딩을 기다리게 한다.
→ **디스크 캐시를 반드시 남긴다.** 위젯별 마지막 성공 응답을 파일로.

**메모리 150MB의 근거:** Tauri 하한선이 WebView 60~80MB. 우리 데이터는 몇 MB.
실제로는 100~120MB 예상. 150MB를 넘으면 뭔가 잘못됐다는 신호.

**측정 노출:** 설정창 "정보" 섹션에 현재 메모리 사용량 + 마지막 폴링 소요 시간 표시.

**Tailwind를 쓰는 이유 (익숙해서가 아니라):** 위젯이 30~50가지 작은 상태
(로딩/에러/stale/드래그중/이월됨/우선순위별)를 가짐. 이런 조합 폭발은 유틸리티 클래스가 유리.
Tailwind 4는 런타임이 없어 메모리 요구에 중립적.
(emotion/styled-components는 런타임이 있어 역행. vanilla-extract는 빌드 복잡도만 증가)

**zod를 넣는 이유:** `board.json` 스키마 마이그레이션. 버전별 스키마를 정의하면 구버전 파일을 안전하게 변환.
손으로 하면 반드시 틀림. (검증 자체는 Rust serde가 하므로 프론트는 최소한으로)

**안 쓰는 것과 이유:**
- `@tanstack/react-query` — Rust가 데이터 소유 (5장)
- `@tanstack/react-router` — 화면이 사실상 하나. Tauri에서 URL은 사용자에게 안 보임
- `@tanstack/react-virtual` — 30건에 가상화는 과잉. 필요해지면 추가
- `sonner` (토스트) — 실패는 위젯/배너에, 성공은 화면 변화로. 토스트가 필요한 순간이 거의 없음
- `framer-motion` — 모달·드래그 정도는 CSS transition으로 충분. 60~100KB + 런타임이 메모리 목표와 충돌

### bun + Tauri
```
패키지 관리   bun install
스크립트      bun run dev / build / test
번들러        Vite (bun이 실행하되 --bun 플래그 없이)
테스트        bun run test → vitest  (bun test 아님)
```

**`--bun` 플래그를 안 쓰는 이유:** bun 호환성 문제가 아니라 **불필요한 전환**.
`@tailwindcss/vite`, `@vitejs/plugin-react`가 Vite 위에서 도는 게 자연스러움.

**`bun test`가 아닌 vitest인 이유:** bun 내장 러너는 Vite 설정(경로 alias, 플러그인)을 공유하지 않음.

**알려진 마찰 (bun 1.3.14에서 대부분 해결됨):**
- `beforeDevCommand` 종료 시 Vite 프로세스가 남는 경우 (시그널 처리)
- 네이티브 애드온 → `trustedDependencies`에 esbuild/lightningcss 등 명시 필요할 수 있음

## 20. 구현 순서

### 1차 — "화면에 내 Jira 티켓이 뜬다"
- Tauri 앱 셸, 창, 빌드 파이프라인
- 보드 + react-grid-layout, 위젯 추가/삭제/이동/리사이즈, 배치 저장
- 위젯 인터페이스 + WidgetShell
- 설정창 — Jira 연결 (URL/이메일/토큰, 키체인, 연결 테스트)

- 로그, 성능 계측

**1차의 목표는 뼈대 검증.** Tauri IPC·키체인·폴링·캐시·그리드·에러 처리가 실제로 동작하는지.
이후 모든 기능은 검증된 뼈대에 얹는 일이라 훨씬 빠르고 안전.

### 2차 — Jira 심화
- 상세보기 모달 + ADF 렌더러 + 코멘트
- 티켓 생성 폼 (createmeta 기반)

**미룬 이유:** 목록만으로도 앱이 쓸모 있음. 1차를 며칠 써보면
"상세보기에 이것도 필요하다"를 알게 되고, 그때 만드는 게 낫다.

### 3차 — 나머지 위젯

- Todo 위젯 (날짜별 + 이월)

**GitHub을 먼저 두는 이유:** GraphQL이라는 새 변수가 있어 먼저 검증.
Todo는 외부 의존이 없어 언제 만들어도 리스크가 같음.

### 4차 — 필요해지면
- 트레이 상주, 백그라운드 폴링, 알림, 자동 시작
- 다중 보드 UI, 다중 연결 UI

- 이미지 첨부 렌더링

## 21. 한 번 뒤집힌 결정들

**기록해두는 이유:** 같은 근거로 같은 결론에 다시 도달하는 것을 막기 위해서다.
아래는 초기 판단이 틀렸다고 판명된 사례이고, 각각 **무엇이 판단을 뒤집었는지**가 핵심이다.

| 뒤집힌 결정 | 뒤집은 근거 |
|---|---|
| PWA + 로컬 서버 → **Tauri** | "self-host"의 뜻이 홈랩 배포가 아니라 자기 기기 전용이었다 |
| react-grid-layout 회피 → **채택** | React 19 경고는 v1 기준의 낡은 정보. v2에서 해소됨 |
| 수동 타입 동기화 → **tauri-specta** | 세팅 비용은 한 번, 타입 불일치는 매번. 후자가 크다 |
| 생성 폼 고정 4필드 → **createmeta 보강** | 한 프로젝트만 보고 판단하려다 다른 프로젝트가 반박 |
| createmeta 보강 → **경고·안전망 역할로 축소** | `hasDefaultValue`를 반영해 실측하니 추가 렌더할 필드가 0개였다 (11.3 정정) |
| 라벨·컴포넌트 열 추가 → **제외** | 실측 표본에서 채움률 0/22 |
| Todo 위젯 8개 → **1개** | 전부 같은 파일을 읽는다. 두 번째는 같은 목록을 한 번 더 그릴 뿐 |
| Todo "완료 항목 정리"(삭제) → **접기** | 목적이 삭제가 아니라 시야 확보였다. 유일본에 삭제 경로를 안 늘린다 |
| 티켓 생성 버튼 앱 타이틀바 → **위젯 헤더** | 앱 전역 동작이 아니라 **그 위젯의 동작**이다. 위젯이 소유한 쿼리·프로젝트 맥락에서 생성이 시작된다 |
| Todo 행 전체 draggable → **손잡이만** | 텍스트·체크박스 조작과 충돌. "누를 때만 켜기"는 React 재조정과 싸우다 두 번 실패 (13장) |
| Jira 조작 "읽기 + 생성만" → **상태 변경 포함** | 우려의 정체는 "워크플로우가 다르다"가 아니라 **"폼을 또 만들어야 한다"**였다. 폼을 안 만드는 답이 있었다 |
| 단일 보드 → **다중 보드 탭** | 전제("위젯 5~7개면 한 화면")는 그대로 참인데 **근거가 교체**됐다. 문제는 면적이 아니라 맥락 전환이었다 |

**타이틀바 → 위젯 헤더 (2026-08-01).** 원래 스펙(D6)은 생성 버튼을 앱 타이틀바에
두었고, 그대로 구현했다가 되돌렸다. 타이틀바는 **앱 전역** 동작이 있는 자리인데
티켓 생성은 그렇지 않다 — 어떤 프로젝트에, 어떤 쿼리 맥락에서 만드는지는 위젯이
가지고 있다. 보드에 Jira 위젯이 둘이면 타이틀바 버튼은 "어느 쪽?"에 답할 수 없다.

`⌘⇧N`은 남기되 **첫 번째 Jira 위젯**을 연다. 단축키는 하나뿐이라 어차피 하나를
골라야 하고, 그 사실을 코드에 적어뒀다.

> 이건 실측이 뒤집은 게 아니라 **스펙을 그대로 따르다 놓친 것**이다.
> 스펙에 있다는 이유로 위치를 의심하지 않았다. 앞의 항목들과 성격이 다르므로
> 따로 적어둔다 — 조회로 막을 수 있는 종류가 아니었다.

**"읽기 + 생성만" → 상태 변경 포함 (2026-08-06).** 11.5는 상태 변경을 뺐고,
근거를 두 개 적었다. 지금 보면 **그 둘의 무게가 달랐다.**

- "워크플로우가 프로젝트마다 다르다"는 애초에 **문제가 아니었다.** 전이 목록을
  조회하면 끝이다. 실측하니 EDU 5개 / DTH 7개로 정말 다르지만, 다르다는 사실이
  구현을 막지는 않는다. 우리는 그저 **묻고 그려주면 된다** — 하드코딩하려 했다면
  막혔겠지만 애초에 그럴 이유가 없었다.
- 진짜 우려는 두 번째였다. "전이에 필수 필드가 걸리면 **또 폼이 필요**"다.
  이건 실제 비용이고, 11.3 생성 폼에서 이미 값을 치른 종류다.

**그래서 뒤집은 것은 "폼을 만들지 않아도 된다"는 발견이다.** 필수 필드가 걸린
전이를 브라우저 링크로 바꾸면 폼 없이 정직해진다. 이 선택지가 처음부터 있었는데,
"상태 변경을 하려면 전이 폼이 필요하다"를 한 묶음으로 받아들여서 보이지 않았다.

> 교훈은 **하나의 결정에 근거를 여러 개 적을 때 무게를 따로 재라**는 것이다.
> 근거 두 개를 나란히 적어두면 둘 다 벽처럼 보인다. 실제로는 하나는 벽이 아니었고,
> 남은 하나는 **우회로가 있는 벽**이었다. 11.5가 "실사용 후 아쉬우면 추가"라고
> 문을 열어둔 것이 이 재검토를 가능하게 했다 — 닫힌 결정으로 적었다면
> 근거를 다시 읽어볼 생각을 안 했을 것이다.

**단일 보드 → 다중 보드 탭 (2026-08-06).** 14장은 탭을 **명시적으로 거부**했다.
이 항목이 앞의 것들과 다른 점은 **원래 결정이 여전히 옳다는 것**이다.

- **전제는 뒤집히지 않았다.** "실제 위젯 수가 5~7개 → 화면 하나에 다 들어간다"는
  지금도 참이다. 실측이 반박하지 않았고 반박할 성질도 아니다
- **경고문도 뒤집히지 않았다.** "탭 뒤에 숨은 위젯은 잊힌다"는 지금도 참이다.
  탭을 만들면서 이 비용을 **없앤 것이 아니라 감수하고 줄였다** (14.2)
- **뒤집힌 것은 근거 하나뿐이다.** "다 보이는데 왜 나누나"에서
  "**지금 볼 것이 상황마다 다르다**"로 바뀌었다

> **교훈: 결정을 뒤집는 것과 근거를 교체하는 것은 다르다.**
> 14장을 다시 읽었을 때 "전제가 틀렸나"부터 확인했는데 전제는 멀쩡했다.
> 틀린 건 **그 전제로 답할 수 있는 질문이 아니었다는 것**이다.
> 원래 결정은 탭을 "위젯을 더 담는 수단"으로 읽고 면적으로 답했다.
> 실제 용도는 "지금 안 볼 것을 치우는 수단"이고, 그건 면적이 아니라
> 주의(attention)의 문제라 위젯 수로는 답이 안 나온다.
> **같은 UI가 목적에 따라 정반대의 판정을 받는다** — 수단만 보고 기각하면
> 목적을 확인할 기회를 잃는다.

이 항목은 앞의 것들과 **뒤집힌 경로도 다르다.** 위 항목 대부분은 API 응답을
조회해서 뒤집혔다. 이건 조회로 알 수 없다 — **"내가 언제 무엇을 보고 싶은가"는
사용자만 아는 사실**이고, 실제로 사용자가 말해줬다.

**틀린 예측도 하나 발견했다.** 14장은 "나중에 쉽게 추가하기 위한 조치" 세 개를
적었는데 **세 번째가 존재하지 않는 것에 기댔다**:

> "Rust 스케줄러가 위젯을 보드 단위로 그룹핑 → 비활성 보드 폴링 중단이
> 한 줄로 들어감"

`scheduler/` 디렉터리는 만들어지지 않았고 폴링은 데이터 훅 안의
`setInterval`이다. 다행히 결과는 예측보다 좋았다 — **폴링 중단이 한 줄도 아니라
0줄**이었다. React 언마운트가 이미 하고 있었다.

> 교훈은 **"나중을 위한 대비"를 적을 때 아직 없는 것을 전제하지 말라**는 것이다.
> 세 조치 중 실제로 값을 한 것은 이미 존재하던 둘(`boards: []` 배열,
> `useActiveBoard()`)이다. 그 둘 덕에 스키마 버전을 안 올렸고 위젯 코드를 한
> 줄도 안 고쳤다. 셋째는 예언이었고, 예언이 안 맞았는데도 손해가 없었던 것은
> 운이다. 대비의 값은 **"지금 코드에 무엇을 심어두는가"**에서 나오고,
> "나중에 무엇을 만들 것인가"에서는 안 나온다.

**공통 교훈:** 위 항목 대부분은 **실제 응답을 조회했을 때** 뒤집혔다.
API 스키마·필드 채움률·라이브러리 버전은 문서나 기억이 아니라 실물로 확인한다.

레이아웃 문제도 마찬가지다. 스크린샷을 눈으로 보고 원인을 추측하면 여러 번 헛짚는다.
브라우저에서 **좌표를 직접 재면** 한 번에 잡힌다 — `alignment.test.tsx`가 그 결과다.

**같은 함정이 드래그에서 재현됐다 (2026-08-02).** 웹 쪽 코드만 읽으며 네 번
헛짚었는데 원인은 `tauri.conf.json`의 `dragDropEnabled`였다. 증상("+ 포인터만
뜬다")이 이미 "웹 이벤트가 아예 안 온다"를 가리키고 있었는데, 코드를 읽고 가설을
세우는 쪽을 먼저 했다. **웹뷰 밖(Tauri 설정·OS 레벨)을 먼저 의심할 것.**

테스트에도 교훈이 있다. 깨진 테스트 7개가 전부 "`pointerdown`이 행의 `draggable`을
켠다"는 **구현 메커니즘**을 단언하고 있어서, 구현이 틀렸을 때 같이 틀렸다.
동작("재조정 뒤에도 다시 끌 수 있는가")을 검증하도록 다시 썼다.

## 22. 배포 — 자체 서명 + 배포 전 검사

**결정:** adhoc 서명(`signingIdentity: "-"`)으로 배포하고, `verify-release.sh`를
릴리즈 절차의 필수 단계로 둔다. Apple 공증은 하지 않는다.

### 왜 검사 단계가 생겼나 (2026-08-05)

**v0.3.0-alpha를 서명되지 않은 채로 배포했다.** 다른 맥에서 받으면
"손상되었기 때문에 열 수 없습니다"가 뜨고, **우클릭→열기로도 안 뚫렸다.**

```
$ codesign --verify --deep --strict my-pegboard.app
code has no resources but signature indicates they must be present

$ ls my-pegboard.app/Contents/_CodeSignature/
없음
```

`Contents/Resources/`는 있는데 그 봉인이 없다. `tauri.conf.json`에 서명 ID가
없어 Tauri가 **번들 서명 단계를 통째로 건너뛴** 결과다. 바이너리에는 링커가
붙인 adhoc 서명이 있어서 겉보기엔 서명된 것처럼 보였다.

### 이 사고가 무서운 이유 — 로컬에서는 멀쩡하다

| | 빌드한 기기 | 받은 기기 |
|---|---|---|
| quarantine | 없음 | **`com.apple.quarantine` 부착** |
| Gatekeeper | 검사 안 함 | **검사 → 깨진 서명 발견** |
| 결과 | 실행됨 | **열리지 않음** |

`run.sh`가 개발 빌드를 따로 서명해주는 것도 착시에 한몫했다. 개발 중에는
서명된 바이너리를 쓰고, `tauri build`는 그 경로를 안 탄다.

> **로컬에서 실행되는 것은 배포 가능하다는 증거가 아니다.**
> 이 명제가 이 장의 전부다.

### 그래서 스크립트로 강제한다

체크리스트만 적으면 안 읽는다. `scripts/verify-release.sh`가 dmg를 마운트해
다섯 가지를 보고 실패 시 exit 1을 낸다:

1. `codesign --verify --deep --strict` — v0.3.0을 무너뜨린 바로 그 검사
2. `_CodeSignature/CodeResources` 존재 — 1이 실패한 **원인**을 짚어준다
3. quarantine을 붙인 사본으로 재검증 — 실제 사용자 조건
4. Gatekeeper 판정의 **사유** 구분 (아래)
5. dmg 파일명 ↔ `Info.plist` 버전 일치

**검사기 자체를 양방향으로 검증했다** — 정상 dmg는 통과하고, `_CodeSignature`를
지운 dmg는 다섯 항목 전부 실패한다. 한 번도 실패해본 적 없는 검사기는 검사기가
아니다.

### Gatekeeper의 `rejected`는 두 종류다

adhoc 서명이므로 `spctl`은 **항상** rejected를 준다. 사유가 갈린다:

| 사유 | 우클릭→열기 | 판정 |
|---|---|---|
| 서명 무효("손상됨") | **안 통함** | 배포 불가 |
| 미공증 | 통함 | **정상** |

스크립트는 이 둘을 구분한다. `rejected`만 보고 실패로 처리하면 정상 빌드도
막힌다.

### 공증(notarization)을 안 하는 이유

Apple Developer 계정이 연 $99다. 얻는 것은 첫 실행 시 우클릭→열기를 안 해도
되는 것뿐이고, 혼자 쓰거나 몇 명에게 주는 앱에서 그 값어치가 안 나온다.
**대신 릴리즈 노트에 우클릭→열기 안내를 매번 적는다** — 조용히 실패하게
두지 않는다(대전제 2).

## 23. 업데이트 — GitHub Release 기반 자동 업데이트

`tauri-plugin-updater` + `tauri-plugin-process`. 앱 안에서 받아 설치하고 재시작한다.

### 23.1 왜 "알림만"이 아니라 진짜 자동 업데이트인가

알림만 두면 사용자가 매번 dmg 받기 → 드래그 → 우클릭→열기 3단계를 겪는다.
받는 사람이 여러 명이면 그 3단계가 사람 수만큼 반복된다. 자동 업데이트의 가치가
정확히 그 3단계를 없애는 것이다.

**대가:** 릴리즈 절차의 영구적 복잡도 증가. `latest.json` 생성과 서명 키 관리가
매 릴리즈에 붙는다. 그래서 검사를 스크립트로 못 박았다 (23.5).

### 23.2 ★ minisign 개인키 — 이 장에서 가장 중요한 것

앱 바이너리에 **공개키를 박아서** 배포한다. 그 앱이 받아들이는 업데이트는
**대응하는 개인키로 서명된 것뿐**이다.

> **개인키 또는 비밀번호를 잃으면 이미 배포된 앱은 영구히 업데이트를 못 받는다.**
> 공개키를 바꾸려면 새 앱을 수동 설치해야 하고, 그건 업데이트 경로가 끊긴 것과 같다.

**키 위치:** 로컬(`~/.tauri/my-pegboard.key`) + **비밀번호 관리자에 파일과 비밀번호 둘 다 백업.**
공개키는 `tauri.conf.json`의 `plugins.updater.pubkey`에 있다(비밀 아님).

**비밀번호를 붙인 이유:** 파일 하나가 유출돼도 그것만으로는 이 앱이 받아들이는
업데이트를 만들 수 없게. 파일과 비밀번호 **둘 다** 있어야 서명된다.

**CI(GitHub Actions)를 쓰지 않은 이유:** 릴리즈를 CI로 옮기려면 자체 서명 인증서도
CI로 이사시켜야 하는데(`scripts/make-signing-cert.md`), 그건 별개의 작업이다.
두 개를 한 번에 하면 실패했을 때 **원인이 updater인지 CI 서명인지 구분이 안 된다.**
이미 서명으로 한 번 데인 영역이다(22장). 나중에 옮기려면 키를 Secrets에 붙여넣으면
되므로 이 선택이 CI로 가는 길을 막지 않는다.

**다른 맥에서 릴리즈하려면** 키를 그 맥으로 옮기면 된다. 하드웨어 고정이 아니라
**키에 종속**이다. 옮기는 걸 잊었을 때가 문제인데 — 그게 아래 조용한 실패다.

### 23.3 ★ 조용한 실패: 키 없이 빌드하면 아무 에러가 안 난다

**개인키가 없으면 `tauri build`는 updater 번들(.app.tar.gz + .sig)을 만들지 않는다.
에러가 아니라 그냥 안 만든다.** dmg는 정상적으로 나온다.

그래서 키 없는 맥에서 릴리즈하면: dmg는 잘 올라가고, `latest.json`이 가리킬 `.sig`가
없어서 **기존 사용자의 앱은 새 버전을 영원히 못 본다.** 빌드한 기기에서는 아무
이상이 없다.

**v0.3.0 서명 사고(22장)와 구조가 똑같다.** 그래서 `verify-release.sh`가 막는다(23.5).

더 나쁜 변형: 다른 맥에서 **새 키를 만들어** 빌드하면 `.sig`도 나오고 `latest.json`도
완성되지만 공개키가 달라 기존 앱이 검증에 실패한다. 사용자는 "업데이트 있음"을 보고
받았는데 설치 단계에서 실패한다. **이건 복구 불가**다 — 그래서 검사 7이 keynum을
비교한다.

### 23.4 확인 시점과 알림 채널

**확인:** 앱 시작 후 **5초 지연** 1회 + **6시간 주기.**
시작 경로에 0ms 영향이어야 한다("켜면 즉시 지난 데이터가 보인다"는 대전제).
릴리즈 빈도가 며칠 단위라 6시간이면 충분하다.

**알림은 타이틀바 ⚙ 아이콘의 점 하나뿐이다. 배너도, 시작 시 모달도 없다.**

| 후보 | 왜 안 썼나 |
|---|---|
| 전역 배너 | 업데이트는 **에러가 아니다.** `AuthBanner`의 danger 채널과 급수를 섞으면 "뭐 잘못됐나"가 된다. 그리고 배너 둘이 동시에 뜨면 보드가 아래로 밀린다 |
| 시작 시 모달 | 켰더니 데이터가 아니라 모달이 보인다 — 대전제와 정면 충돌 |
| 주기 조회 중 모달 | 작업 중 갑자기 화면을 덮는다. 티켓 생성 폼을 쓰던 중이면 최악 |
| 네이티브 알림 | 4차 작업. 이 구조 위에 나중에 얹으면 된다 |

**dismiss 없음.** 배지가 유일한 알림 채널이므로 끌 수 있게 만들면 알림이 사라진다.
점 하나는 소음이 아니고, 업데이트하면 사라진다. "dismiss한 버전"을 저장할 이유가 없다.

**배지가 켜져 있으면 설정창이 `정보` 탭으로 열린다** (클릭·⌘, 모두).
알려야 할 게 있으면 그것부터 보여준다 — 배지를 보고 누른 사람은 배지에 대한 답을
기대한다.

### 23.5 릴리즈 절차와 검사

**endpoint:** `https://github.com/DevooKim/my-pegboard/releases/latest/download/latest.json`

**⚠️ `--prerelease`를 붙이지 않는다.** GitHub의 `/releases/latest`는 **prerelease를
건너뛴다.** alpha만 올리던 기존 방식대로면 이 URL이 404다. 태그 이름의 `-alpha`
접미사는 그대로 두므로 "아직 알파"라는 신호는 유지된다. 잃는 것은 릴리즈 페이지의
"Pre-release" 배지뿐이다.

**`latest.json`은 손으로 만들지 않는다** — `scripts/make-latest-json.sh`.
서명이 수백 자이고 버전·URL·파일명이 세 군데서 일치해야 하는데, **틀려도 빌드는
성공한다.** 사용자가 "업데이트 없음"을 겪을 때까지 아무도 모른다.

이 스크립트는 tauri가 만든 `my-pegboard.app.tar.gz`를 **버전이 들어간 이름으로
복사**한다. 원래 이름에 버전이 없어서, 그대로 올리면 릴리즈마다 같은 이름의 에셋이
쌓여 어느 버전인지 구분되지 않는다.

**`verify-release.sh`의 updater 검사 4개 (6~9):**

| # | 검사 | 막는 사고 |
|---|---|---|
| 6 | `.app.tar.gz` + `.sig` 존재 | 키 없는 맥에서 빌드 (23.3) |
| 7 | `.sig`의 keynum == 앱 pubkey의 keynum | 다른 키로 서명 → 복구 불가 사고 |
| 8 | `latest.json` version == `tauri.conf.json` version | 엉뚱한 버전 배포 |
| 9 | URL이 가리키는 파일이 번들에 실재 + 태그가 `v{version}` | updater가 404 → 조용히 "업데이트 없음" |

검사 7은 minisign 파일을 base64로 한 겹 벗겨 keynum 8바이트를 비교한다.
**실제로 다른 키로 서명해 불일치가 잡히는지 확인했다** — 검사가 통과만 하는지 보고
넘기면, 잡지 못하는 검사를 "커버됨"으로 착각한다.

### 23.6 설치와 재시작

**진행률을 그리지 않는다.** dmg가 **6MB**라 정상이면 1~3초에 끝난다. 42%를 볼 시간이
없다. 대신 **60초 타임아웃**을 둔다 — 영원히 도는 스피너가 조용한 실패다.

**재시작 시점은 사용자가 고른다.** `[지금 재시작] [나중에]`.
"나중에"를 골라도 파일은 이미 교체됐으므로 다음 실행이 새 버전이다.

**재시작 전에 디바운스 대기 중인 배치 저장을 강제 flush한다**
(`flushPendingSaves()`). 안 하면 드래그로 위젯을 옮긴 직후 재시작할 때 그 변경이
조용히 사라진다. Todo는 해당 없다 — 모든 변경이 즉시 Rust로 가서 대기분이 없다.

**실패 처리:**

| 실패 | 화면 | 출구 |
|---|---|---|
| 네트워크·타임아웃 | 사유 그대로 | `[다시 시도]` |
| **서명 검증 실패** | "업데이트 파일을 검증할 수 없습니다" | **`[릴리즈 페이지에서 직접 받기]`** |

서명 검증 실패에 재시도 버튼을 주면 안 된다 — 몇 번 눌러도 같은 결과다.
앱 안에서 할 수 있는 게 없으므로 릴리즈 페이지가 유일한 출구다.
**23.3의 키 불일치 사고가 났을 때 사용자가 갇히지 않는 유일한 길이다.**

### 23.7 검증의 한계 (정직하게 남김)

빌드 → `latest.json` 생성 → 검사 9개 통과까지 **실제 릴리즈 빌드로 확인했다.**
검사 6이 키 없을 때 exit 1을 내는 것과 검사 7이 다른 키를 잡아내는 것도 확인했다.

**아직 확인하지 못한 것: 다운로드 → 설치 → 재시작 전체 경로.**
더 높은 버전의 릴리즈가 있어야 테스트되므로, v0.4.0-alpha를 실제로 올려
v0.3.1-alpha 설치본에서 확인해야 한다. **그때까지 이 경로는 미검증이다.**
실패해도 dmg 수동 설치라는 기존 경로가 살아 있어 대가는 낮다.

## 24. 앨범 위젯 — 로컬 사진 배경

**결정:** 로컬 폴더(또는 고른 파일들)의 사진을 셔플 순서로 순환시키는 위젯.
`asset:` 프로토콜로 네이티브가 원본을 스트리밍하고, 스코프는 **사용자가 고른
경로만** 런타임에 열어준다.

### 24.1 성격 — 뷰어가 아니라 배경

작업용 대시보드 한쪽에서 사진이 조용히 바뀐다. 그게 전부다.
그래서 **일부러 만들지 않은 것들**이 있다:

| 안 만든 것 | 왜 |
|---|---|
| 파일명·촬영일·EXIF 표시 | 배경을 보다가 파일명을 읽지 않는다. 넣으면 사진을 가린다 |
| 썸네일 그리드 | 위젯 4×8칸에 격자를 넣으면 사진이 우표가 된다 |
| 확대보기·상세 모달 | 미리보기 앱이 훨씬 낫다 |
| 정렬 순서 선택 | 셔플이 목적이다. "파일명순으로 보기"는 파인더의 일 |
| 전환 효과 선택 | 고를 것이 늘어나는 것 자체가 배경 위젯의 부담이다 |

**GitHub 상세 모달을 안 만든 것과 같은 논리(12.5)다.** Jira에 상세를 만든 건
회사 Jira 웹이 느려서인데, 사진은 그 전제가 없다 — macOS 미리보기는 즉시 열린다.
우리가 어설픈 뷰어를 만들면 배경도 뷰어도 아닌 것이 된다.

**상호작용은 하나뿐: 위젯 면적 전체 클릭 = 다음 장.** 화살표 버튼을 놓으면
작은 위젯에서 사진의 상당 부분을 가린다. 누를 만한 것이 하나뿐이므로
면적 전체를 주는 것이 맞다.

### 24.2 ★ 이미지 전달 — `asset:` 프로토콜과 빈 스코프

이 장에서 가장 조용히 깨지는 부분이다.

**base64로 내리지 않는다.** 사진 한 장이 3~8MB고, IPC로 실어 보내면 base64 팽창
33%까지 얹혀 한 장에 10MB가 웹뷰로 넘어온다. DECISIONS 6이 Jira 응답을
"필요한 필드만 남겨서" 1/10로 줄이는 것과 정면으로 충돌한다. 순환 주기가
10초면 10초마다 그 짓을 한다.

대신 `convertFileSrc(path)`로 `asset://localhost/...`를 만들어 `<img src>`에
넣는다. **네이티브가 파일을 스트리밍하므로 IPC 페이로드가 0이고 원본 화질이
그대로 나온다.** 리사이즈도, `image` crate도, 썸네일 캐시도 필요 없다.

**대가는 스코프다. 그리고 이게 함정이다:**

`tauri.conf.json`의 CSP는 이미 `img-src ... asset: http://asset.localhost`를
허용하고 있었다. **CSP만 보고 "허용돼 있네"라고 판단하면 틀린다** — CSP는
"웹뷰가 이 스킴을 불러도 된다"만 말하고, `assetProtocol.enable`이 꺼져 있으면
그 스킴을 처리할 핸들러 자체가 없다. `convertFileSrc()`는 **에러 없이** URL을
만들고, `<img>`는 **에러 없이** 깨진 이미지가 된다. web 위젯 iframe이 차단당해
빈 화면이 되는 것과 같은 종류의 조용한 실패다.

그래서 셋을 함께 켰다:

1. `Cargo.toml`의 `tauri`에 **`protocol-asset` feature** — 없으면
   `asset_protocol_scope()`가 컴파일되지 않는다. `tauri-plugin-fs`는 필요 없다.
   코어 기능이다
2. `tauri.conf.json`에 `app.security.assetProtocol = { enable: true, scope: [] }`
3. 런타임 스코프 추가 — `fs::Scope::allow_directory(path, false)` / `allow_file(path)`

**정적 scope를 빈 배열로 둔 이유:** `$HOME/**`를 넣으면 웹뷰가 사용자 홈 전체를
읽을 수 있게 된다. 사진 위젯 하나가 요구할 권한이 아니다. 기본으로는 아무 경로도
열리지 않고, 사용자가 폴더를 고른 그 순간에 **그 경로만** 열린다. 폴더는
**비재귀**로 허용하고(스캔이 비재귀이므로), 파일 목록은 디렉터리가 아니라
**파일 단위**로 허용한다 — 디렉터리를 열면 고르지 않은 형제 파일까지 읽힌다.

### 24.3 ★★ 재시작 복원 — 찾기 가장 어려운 실패

**런타임 스코프는 메모리에만 있다. 앱을 껐다 켜면 사라진다.**

`board.json`에 저장된 경로는 그대로 남아 있으므로 위젯은 사진 경로를 알고 있고,
`<img>`도 URL을 만들어 넣는다. 그런데 스코프가 없어서 **깨진 이미지**가 된다.
CSP는 `asset:`을 허용하므로 콘솔에도 아무 말이 없다.

**개발 중에는 절대 재현되지 않는다.** 위젯을 방금 만들었으므로 런타임 허용이
살아 있다. "어제는 됐는데 오늘 아침에 안 된다"로만 나타난다.

그래서 `lib.rs`의 setup이 `restore_scopes()`로 board.json의 **모든** 앨범 위젯을
훑어 다시 허용한다. `Files` 위젯은 **파일을 하나도 빠뜨리면 안 되는데**, 빠진
그 한 장만 안 보이므로 눈으로는 거의 못 잡는다.

**그래서 테스트가 있다** (`providers/album/tests/mod.rs`의
`restore_covers_every_path_of_every_album_widget`). Folder 위젯과 Files 위젯이
섞인 board.json에서 펼쳐진 경로 집합 전체를 단언한다 — 빠뜨림도 여분도 잡는다.
여러 보드에 흩어져 있어도 훑고(다중 보드는 UI만 없다, 14장), 파싱할 수 없는
소스나 아직 안 고른 위젯이 있어도 앱 시작을 멈추지 않는다.

### 24.4 폴더 선택을 Rust가 한다

`tauri-plugin-dialog`에는 JS 쪽 npm 패키지가 있고 그걸 쓰면 프론트 코드가 짧다.
**쓰지 않았다.** 그러면 셋이 프론트로 흘러온다: 다이얼로그 호출, 스코프 허용,
폴더 스캔. 스코프 허용은 Rust만 할 수 있으므로 결국 IPC 왕복이 두 번이 되고,
그 사이에 **"경로는 골랐는데 스코프가 아직 없는" 상태**가 존재하게 된다.

커맨드 하나(`album_pick_folder` / `album_pick_files`)가
**다이얼로그 → 스코프 허용 → 스캔 → 캐시 저장**을 전부 하고 결과만 내려보낸다.
npm 의존성 0개고, capabilities에 dialog 권한도 필요 없다 — 프론트가 플러그인을
직접 부르지 않으므로. "Rust가 데이터의 주인"과 정확히 맞는다.

`blocking_pick_folder`는 메인 스레드에서 부르면 교착한다. Tauri는 `async`
커맨드를 별도 스레드에서 돌리므로 `async fn`으로 만들었다.

### 24.5 스캔 — 비재귀 · 1000장 · 확장자만

| 규칙 | 왜 |
|---|---|
| **비재귀** | `~/Pictures` 하나만 재귀해도 라이브러리 전체(수만 장)를 만난다. 스캔이 앱 시작을 붙잡는다. 폴더를 고른다는 건 "그 폴더에 있는 것"을 보고 싶다는 뜻이다 |
| **상한 1000장** | 10초 주기로 2.7시간이다. 배경으로 충분히 다양하다. 진짜 이유는 IPC 페이로드와 셔플 배열이 무한정 커지지 않게 |
| **확장자만 본다** | 매직 바이트를 읽으려면 파일 1000개를 연다. 그 비용으로 얻는 건 "확장자를 속인 파일" 걸러내기뿐이고, 그건 `<img onError>`가 이미 잡는다 |
| **대소문자 무시** | 카메라·스캐너가 `.JPG`를 쓴다. 빠뜨리면 **에러 없이 폴더 전체가 빈 것처럼 보인다** |
| **숨김 파일 제외** | `.DS_Store`가 대표적. `.hidden.jpg`도 사용자가 보이길 기대하지 않는다 |
| **파일명순 정렬** | `read_dir`의 순서는 파일시스템이 정하고 보장이 없다. 같은 폴더를 두 번 훑으면 같은 순서가 나와야 한다 |

**상한 초과분은 `skipped`로 화면에 드러낸다** — "42장은 표시하지 않음 (1000장 상한)".
조용히 자르면 사용자는 없는 사진을 계속 기다린다.

**`image` crate를 쓰지 않는다.** 리사이즈도 EXIF 파싱도 안 한다. `<img>`가 대개
EXIF 회전을 존중하고, 원본을 스트리밍하므로 썸네일을 만들 이유가 없다.

### 24.6 셔플 — 순서를 만들어 그 순서로 돈다

`photos[Math.floor(Math.random() * n)]`은 짧지만 **같은 사진이 연달아 나온다.**
사진이 10장이면 두 번 연속 같은 장이 나올 확률이 10%다. 곁눈으로 보는 배경
위젯에서 그건 "안 바뀌었다 = 고장났다"로 읽힌다.

그래서 음악 플레이어의 셔플과 같다: **목록을 한 번 섞어 고정 순서를 만들고 그
순서로 돈다. 한 바퀴를 다 돌면 다시 섞는다.** 전체를 보기 전에는 같은 사진이
두 번 나오지 않는다. 두 바퀴째에 다시 섞는 이유는 같은 순서를 반복하면
"다음에 뭐 나올지 아는" 상태가 되기 때문이다.

**셔플은 React가 한다.** Rust에 `rand` 의존성을 추가하지 않는다 —
목록이 진실이고 셔플은 **표시 순서**일 뿐이다(5장의 경계).
순서는 `photos`의 인덱스 배열이라 사진 1000장이어도 배열 하나가 늘 뿐이다.

**순서를 디스크에 저장하지 않는다.** 세션 동안만 유지되고 재시작하면 새로
섞인다. 저장하면 board.json에 사진 1000개의 순열이 들어간다.

### 24.7 `prefers-reduced-motion` — 페이드만 끄면 부족하다

크로스페이드 300ms는 전역 CSS의 `@media (prefers-reduced-motion: reduce)`가
0.01ms로 줄여서 즉시 교체가 된다. 여기까지는 자동이다.

**그런데 자동 순환도 멈춰야 한다.** 10초마다 화면이 바뀌는 것은 페이드와 별개로
그 자체가 움직임이다. 그 설정을 켠 사용자는 "가만히 있어라"를 말한 것이므로,
페이드만 끄고 계속 도는 건 설정을 반쯤 무시하는 것이다. 그래서 View가 JS에서
`matchMedia`를 보고 타이머를 걸지 않는다. **누르면 여전히 넘어간다** — 사용자가
직접 누른 것은 사용자의 뜻이다.

`matchMedia`의 `change`를 듣는다. 한 번 읽고 끝내면 설정을 켜도 앱을 다시 켤
때까지 계속 움직인다.

### 24.8 실패 — 배경으로서 계속 돌면서 드러낸다

| 실패 | 처리 |
|---|---|
| 한 장이 깨짐/사라짐 | `<img onError>`가 **즉시 다음 장으로**. 동시에 하단에 "N장을 표시할 수 없습니다" |
| 전부 깨짐 | 본문을 에러 상태로 + **경로 표시** + 다시 고르라는 안내 |
| 폴더 접근 불가 | 같음. 메시지에 경로가 들어 있다 — 외장 디스크가 빠진 것인지 폴더를 옮긴 것인지는 경로를 봐야 안다 |
| 폴더 미설정 | 빈 상태에 **`[폴더 선택]` `[사진 선택]`** — 설정창을 열지 않아도 되게 |
| 폴더가 비었음 | "표시할 사진이 없습니다" + 경로 + 지원 확장자 + "하위 폴더는 보지 않습니다" |

**멈추지 않고 넘어가되 개수를 드러내는 것**이 핵심이다. 멈추면 배경으로서
고장난 것이고, 조용히 건너뛰면 사용자는 사진 몇 장이 없어진 것을 모른다.

**로컬 파일시스템의 실패는 전부 영구적이다.** Jira·GitHub의 429/5xx처럼 기다리면
풀리는 종류가 없다 — 사용자가 디스크를 다시 꽂거나 폴더를 다시 고르는 것 말고는
길이 없다. 그래서 `AlbumError`에 `ErrorKind` 축이 없다.

**단, 캐시된 사진은 계속 보여준다.** 외장 디스크나 NAS는 잠들어 있으면 스캔이
수 초 걸리고 분리돼 있으면 아예 실패한다. 그동안 사진이 사라지면 배경으로서
고장난 것이다 — 16장의 "목록을 비우지 않는다"가 여기서도 그대로 적용된다.

### 24.9 캐시 · 폴링

`storage/cache.rs`의 위젯 id별 JSON 캐시를 다른 위젯과 똑같이 쓴다.
앱 시작 시 `album_cached()`로 지난 목록을 먼저 읽어 **즉시 첫 장을 그리고**,
그 뒤에 백그라운드로 한 번 재스캔한다 (17장의 0ms 약속).

**주기 폴링은 없다.** 사진 폴더는 5분마다 바뀌지 않는다. 새로고침 버튼(`pollable: true`)이
재스캔이고 그것으로 충분하다. 설정의 `intervalSecs`는 **사진을 넘기는 주기**이지
데이터를 다시 가져오는 주기가 아니라서, 그 타이머는 View가 소유한다.

`useAlbumData`가 설정 전체가 아니라 **소스만** 받는 이유도 이것이다. 설정 전체를
의존성에 넣으면 사용자가 주기를 3초에서 4초로 고칠 때마다 외장 디스크를 깨운다.

### 24.10 인스턴스 4개 — Todo와 다르다

Todo가 1개인 이유는 모든 위젯이 같은 `todos.json`을 읽어서다(3장·21장).
앨범은 **폴더가 다르면 다른 내용**이다. 여행 사진과 작업 스크린샷을 나란히
놓는 것에 의미가 있으므로 4개다.

### 24.11 설정 타입은 프론트가 소유한다

GitHub 위젯은 `GithubWidgetConfig`를 Rust가 소유한다 — 쿼리·범위·최대 건수를
전부 Rust가 해석하기 때문이다. 앨범은 반대다. Rust가 설정에서 쓰는 것은
`source`뿐이고, 제목과 순환 주기는 **표시 방식**이라 Rust가 알 이유가 없다.
알게 만들면 순환 주기를 바꿀 때마다 폴더를 다시 훑는 코드가 되기 쉽다.

`AlbumSource`만 Rust에서 온다 — IPC 양쪽이 같은 모양을 알아야 하는 것은 그것뿐이다.

### 24.12 소스가 둘뿐인 이유

```rust
enum AlbumSource {
  Folder { path: String },
  Files { paths: Vec<String> },
}
```

**"고정 한 장 배경" 모드를 따로 만들지 않았다.** `Files`에 하나만 담으면 자연히
그게 된다. 모드를 늘리면 설정 UI가 늘고 사용자가 "지금 어느 모드지"를 기억해야
한다. 사진이 한 장일 때는 View가 알아서 "다음 장" 버튼을 잠근다 — 넘길 곳이
없는데 눌리는 버튼은 고장으로 읽힌다.

### 24.13 검증되지 않은 것 (정직하게 남김)

`cargo test` / `bun run test`는 스캔·상한·확장자·스코프 복원·셔플·reduced-motion을
덮는다. **덮지 못하는 것은 `asset:`으로 실제 이미지가 그려지는가**다.

- **브라우저 dev 서버에는 `asset:` 프로토콜이 없다.** 원리적으로 확인할 수 없어서
  View가 그 상태를 감지해 "브라우저에서는 로컬 사진을 표시할 수 없습니다"를 그린다
- jsdom 테스트는 `convertFileSrc`를 mock한다. "어느 경로로 `<img>`를 만들었나"까지만 본다

즉 **스코프 설정이 실제로 맞는지는 앱에서만 확인된다.** 그리고 재시작 복원은
개발 중에 재현되지 않는다(24.3). 그래서 앨범 위젯을 만지고 나면 반드시
**앱을 껐다 켜서 사진이 여전히 뜨는지** 확인한다.
