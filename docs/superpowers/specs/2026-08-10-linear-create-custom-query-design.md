# Linear 생성·커스텀 쿼리와 티켓 ID 복사 설계

작성일: 2026-08-10

## 목표

- Jira와 Linear 상세 모달 헤더의 티켓 ID를 클릭하면 ID를 복사한다.
- Linear 위젯 헤더에서 기본 필드를 갖춘 티켓을 생성한다.
- Linear 위젯 설정에서 타입화된 커스텀 필터를 구성한다.
- Linear의 서버 정렬 범위 안에서 생성일·수정일의 최신순·오래된순을 정확히 제공한다.
- 캐시 우선 표시, 조용한 실패 금지, 토큰 비노출 원칙을 유지한다.

## 범위 밖

- Linear 상세 모달에서 하위 이슈 생성
- 커스텀 필터의 AND/OR 중첩 그룹
- GraphQL 또는 `IssueFilter` JSON 직접 입력
- Linear API가 지원하지 않는 우선순위·마감일·상태 서버 정렬
- 생성 후 낙관적으로 목록에 행 추가
- 첨부 파일, 코멘트, 사이클 지정

## 1. 티켓 ID 복사

Jira와 Linear의 상세 모달 헤더에서 티켓 ID 텍스트를 실제 `button`으로 바꾼다. 클릭하면 화면에 보이는 식별자만 `navigator.clipboard.writeText`로 복사한다.

성공하면 버튼을 1.5초 동안 체크 아이콘과 `복사됨` 상태로 바꾼다. 실패하면 헤더 안에 `복사하지 못했습니다`를 남겨 실패를 드러낸다. 컴포넌트가 닫힐 때 상태 복구 타이머를 정리한다. Jira와 Linear 구현은 각 위젯 폴더에 두어 한 위젯이 다른 위젯 구현에 의존하지 않게 한다.

접근성 계약은 다음과 같다.

- 기본 접근 가능한 이름: `<식별자> 복사`
- 성공 상태 이름: `<식별자> 복사됨`
- 키보드 Enter/Space 지원
- 기존 `ticket-key` 서체와 헤더 시각 구조 유지

## 2. Linear 커스텀 쿼리

### 설정 모델

`LinearQuery`에 기존 `Preset`과 별도로 `Custom` 변형을 추가한다. 커스텀 쿼리는 외부 API JSON을 저장하지 않고 다음 조건을 명시적인 타입으로 저장한다.

- 팀 ID 목록
- 담당 관계: 제한 없음, 나에게 할당, 미할당
- 상태 유형 목록
- 프로젝트 ID 목록
- 라벨 ID 목록
- 우선순위 목록
- 생성일 시작·종료
- 수정일 시작·종료

모든 조건은 AND로 결합한다. 한 필드 안에서 여러 값을 고르면 그 값들은 OR 의미의 `in` 비교가 된다. 날짜는 로컬 날짜 입력을 경계가 명확한 ISO 8601 값으로 바꿔 저장하거나 전송하며, 시작은 포함(`gte`), 종료는 해당 로컬 날짜의 끝까지 포함(`lte`)한다.

팀 범위는 커스텀 조건 안에만 둔다. 기존 `config.teams`는 프리셋 쿼리에 계속 사용하고 기존 board 데이터와 호환한다. 커스텀 쿼리로 전환할 때 현재 팀 범위를 초기값으로 복사할 수 있지만, 이후 두 값을 동시에 적용하지 않는다.

전체 조건이 비어 있으면 저장과 실행을 막는다. 빈 필터가 조직 전체 이슈를 조회하는 조용한 오작동이 되기 때문이다. 알 수 없는 ID, 역전된 날짜 범위, 허용 범위 밖 우선순위도 Rust 경계에서 영구 오류로 거부한다.

### 필터 생성

프론트는 타입화된 설정만 IPC로 보낸다. Rust provider가 이를 Linear `IssueFilter` JSON으로 변환한다.

- 팀·프로젝트·라벨은 관계 객체의 ID `in` 비교로 변환한다.
- 상태는 `state.type`의 `in` 비교로 변환한다.
- 우선순위는 숫자 `in` 비교로 변환한다.
- 미할당은 assignee의 null 비교로 변환한다.
- 나에게 할당은 인증된 viewer ID를 조회해 assignee ID 비교로 변환한다.
- 생성일·수정일은 날짜 비교 객체로 변환한다.

커스텀 쿼리는 항상 최상위 `issues(filter:)` 연결을 사용한다. viewer ID가 필요한 경우 Rust가 조회하고 프론트에는 토큰을 노출하지 않는다.

### 설정 UI

쿼리 선택에 `직접 구성`을 추가한다. 선택하면 핵심 조건 편집 UI를 표시한다. AND/OR 빌더는 만들지 않고 모든 항목이 동시에 적용된다는 문구를 표시한다.

선택지는 Linear 메타데이터 커맨드에서 가져온다. 디스크 캐시가 있으면 즉시 표시하고 뒤에서 조용히 갱신하지 않는다. 사용자가 새로고침을 누를 때 명시적으로 다시 가져온다. 조회 실패, 인증 실패, API 상한으로 잘린 목록은 폼 안에 표시한다.

## 3. Linear 정렬 방향

Linear 서버가 지원하는 정렬 필드는 `updatedAt`과 `createdAt`뿐이므로 필드 범위는 늘리지 않는다. 설정 UI를 정렬 필드와 방향으로 분리한다.

- 필드: 최근 수정, 최근 생성
- 방향: 최신순, 오래된순

최신순은 현재처럼 `first`와 `after`를 사용한다. 오래된순은 연결의 반대쪽에서 정확한 N건을 받도록 `last`와 `before`를 사용하고, 응답을 화면의 오래된순으로 뒤집는다. 쿼리는 `pageInfo`의 양방향 필드 `hasNextPage`, `endCursor`, `hasPreviousPage`, `startCursor`를 요청한다.

`hasMore`는 최신순에서 `hasNextPage`, 오래된순에서 `hasPreviousPage`로 계산한다. 받은 N건만 클라이언트에서 임의 정렬하지 않으므로 설정 UI가 실제 서버 결과와 일치한다.

기존 config에 방향이 없으면 최신순을 기본값으로 적용해 기존 동작을 보존한다.

## 4. Linear 티켓 생성

### 진입점과 폼

Linear 연결이 설정돼 있으면 각 Linear 위젯 헤더에 생성 버튼을 표시한다. 버튼은 해당 위젯의 `LinearCreateIssueModal`을 연다. 첫 버전에는 전역 단축키와 상세 모달의 하위 이슈 생성을 추가하지 않는다.

폼 필드는 다음과 같다.

- 팀: 필수
- 제목: 필수
- 설명: 선택, Markdown 평문 입력
- 상태: 선택, 미선택 시 Linear 기본 상태
- 담당자: 선택
- 우선순위: 선택
- 프로젝트: 선택

팀을 바꾸면 상태·담당자·프로젝트 선택지를 해당 팀 기준으로 다시 구성하고 유효하지 않은 기존 선택을 비운다. 상태 목록은 기존 팀별 조회 흐름을 재사용한다. 생성 폼의 메타데이터도 캐시를 먼저 표시하고 실패를 폼 안에 남긴다.

### mutation과 응답

Rust provider가 `issueCreate(input:)` mutation을 소유한다. 프론트는 타입화된 생성 입력만 넘긴다. 서버 응답의 HTTP 상태뿐 아니라 GraphQL `errors`, mutation의 `success`, 생성된 issue 존재를 모두 확인한다.

성공 응답에는 생성된 이슈의 UUID, 식별자, 제목, URL과 상세 모달 골격에 필요한 목록 필드를 포함한다. 폼을 닫고 생성된 이슈의 상세 모달을 즉시 연다. 동시에 `pegboard:linear-created` 이벤트를 보내 활성 보드의 Linear 위젯들이 서버 결과를 다시 조회하게 한다. 새 이슈가 현재 필터에 포함된다고 가정해 목록에 낙관적으로 삽입하지 않는다.

### 중복 방지와 오류

`issueCreate`는 멱등이 아니므로 자동 재시도하지 않는다.

- GraphQL 검증 오류, 인증 오류, 명시적인 `success: false`: 생성되지 않은 영구 실패로 표시한다.
- 요청 전송 후 응답을 확정할 수 없는 네트워크·타임아웃·5xx: 이미 생성됐을 가능성이 있는 실패로 표시한다.
- 생성됐을 가능성이 있으면 생성 버튼을 잠그고 Linear에서 확인할 행동을 제공한다.
- rate limit처럼 서버가 명시적으로 거절한 응답은 기존 Linear 오류 분류를 따르되 자동 재시도하지 않는다.

오류 원문은 폼 안에 남긴다. 인증 실패는 기존 전역 Linear 인증 배너도 한 번만 활성화한다.

## 5. 메타데이터와 캐시

기존 `linear_meta.json` 저장소를 확장해 설정·생성 폼에 필요한 선택지를 보관한다.

- 팀 목록
- viewer 식별 정보
- 팀별 상태 목록
- 팀별 멤버 목록
- 팀별 프로젝트 목록
- 라벨 목록

파일은 기존 저장 계층의 원자적 쓰기와 스키마 버전을 유지한다. 각 목록에는 가져온 시각과 API 상한 때문에 잘렸는지 여부를 둔다. 팀별 데이터는 팀 ID를 캐시 키로 사용한다. 메타데이터 실패가 기존 캐시를 지우지 않으며, 캐시가 낡았다는 사실과 새로고침 실패를 함께 표시한다.

API 응답에서는 폼이 쓰는 필드만 평평하게 만들어 IPC로 전달한다. 토큰은 계속 Keychain에만 있고 WebView로 내려오지 않는다.

## 6. 결정 문서 갱신

구현과 함께 `docs/DECISIONS.md` 25장을 개정한다.

- Linear 조작 범위를 읽기 + 생성 + 상태 변경 + 상세로 변경
- 직접 입력 없음 결정을 타입화된 핵심 필터 UI 허용으로 변경
- JSON 직접 입력과 AND/OR 중첩을 계속 제외하는 이유 기록
- 정렬 필드 두 종류 제한과 양방향 페이지 조회 기록
- 생성 mutation의 자동 재시도 금지와 생성 여부 불명 오류 처리 기록

`CLAUDE.md`의 Linear 생성·생 필터 관련 설명도 같은 결정과 모순되지 않도록 갱신한다.

## 7. 테스트와 완료 조건

### Rust

- 각 커스텀 조건이 올바른 `IssueFilter`로 변환된다.
- 여러 조건이 AND로 병합되고 다중 값은 `in`으로 변환된다.
- 빈 필터, 잘못된 ID, 역전 날짜, 잘못된 우선순위를 거부한다.
- 나에게 할당 조건이 viewer ID를 사용한다.
- 최신순과 오래된순이 올바른 페이지 변수와 `hasMore`를 사용한다.
- 오래된순 응답을 올바른 표시 순서로 뒤집는다.
- 생성 성공, `success: false`, GraphQL 오류, 인증 오류, 생성 여부 불명 오류를 구분한다.
- 메타데이터 캐시가 디스크 왕복 후 유지되고 실패 시 기존 값을 보존한다.

### React

- Jira와 Linear ID 복사의 성공·실패·상태 복구를 검증한다.
- 프리셋과 커스텀 쿼리 전환, 핵심 조건 편집, 빈 조건 오류를 검증한다.
- 정렬 필드와 방향 변경이 config에 반영된다.
- 생성 폼의 필수값, 팀 변경 시 종속 선택 초기화, 선택 필드 전송을 검증한다.
- 생성 성공 후 상세 모달과 재조회 이벤트가 발생한다.
- 생성 여부 불명 오류에서 중복 생성 버튼이 잠긴다.
- 메타데이터 조회·복사 실패가 화면에 보인다.

### 전체 검증

- specta TypeScript 바인딩 재생성
- `bun run typecheck`
- `bun run lint`
- `bun run test`
- `cargo test` in `src-tauri`

실제 Linear API 호출이나 Tauri 앱 실행 검증은 이 작업에서 수행하지 않는다. 공개 스키마 기반 fixture, Rust 단위 테스트, React 단위 테스트, 정적 검사와 빌드만 수행한다.

## 8. 보드 설정 Import/Export

### 범위와 파일 형식

설정 모달에 `보드` 탭을 추가한다. 내보내기 파일은 다음 봉투만 포함한다.

```json
{
  "formatVersion": 1,
  "exportedAt": "2026-08-10T00:00:00Z",
  "board": { "version": 1, "activeBoardId": "default", "boards": [] }
}
```

보드, 레이아웃, 위젯 설정만 대상이다. 토큰, 이메일, API 키, Todo 원본 데이터, API 응답 캐시는 구조상 포함하지 않는다. 앨범의 로컬 절대 경로는 위젯 설정 일부이므로 보존하지만, 가져오기 미리보기에서 존재하지 않는 경로를 모두 경고한다.

### Rust 소유권과 미리보기

파일 다이얼로그, JSON 읽기·쓰기, 스키마 검증, 병합, 원자적 저장은 Rust가 소유한다. 내보내기는 날짜가 포함된 기본 파일명을 제안하고 취소 시 `None`을 반환한다.

가져오기는 파일 선택 직후 적용하지 않는다. Rust가 파싱한 후보와 다음 미리보기를 IPC로 반환한다.

- 보드 수와 전체 위젯 수
- 위젯 종류별 개수
- 가져오기 파일과 board 스키마 버전
- 존재하지 않는 앨범 폴더·파일 경로

손상 JSON, 지원하지 않는 미래 버전, 빈 보드 배열, 중복 보드·위젯 ID, 알 수 없는 위젯 타입, 보드별 위젯 상한 초과는 적용 전에 거부한다. 경로가 없는 앨범은 경고만 하고 가져오기는 허용한다.

### 교체와 병합

사용자는 미리보기에서 `교체` 또는 `병합`을 고르고 확인한 뒤 적용한다.

- 교체: 가져온 `BoardFile` 전체를 현재 보드로 사용한다.
- 병합: 가져온 모든 보드 ID와 위젯 ID를 새 UUID로 바꿔 기존 캐시 키와 충돌하지 않게 한다.
- 병합 이름 충돌: `업무 (가져옴 2)`, `업무 (가져옴 3)`처럼 결정적으로 해소한다.
- 병합 성공 후 첫 번째로 가져온 보드를 활성화한다.

적용 전에 pending frontend board save를 flush한다. 보드 잠금 안에서 완성된 후보와
모든 앨범 경로의 Tauri escaped pattern을 임시·순수 검증 경로로 확인한 뒤 원자적으로
디스크에 쓰고 메모리 `BoardStore`를 교체한다. 저장이 실패하면 기존 메모리와 기존
`board.json`을 그대로 유지하며 live global asset scope도 변하지 않는다. Tauri
2.11.5는 허용 패턴을 제거할 수 없고 `forbid_*`가 허용보다 우선하므로 import가
runtime scope를 추가·철회하지 않는 것이 필수다. 앨범 scope membership이 달라지면
typed `relaunchRequired` 신호를 반환하고 설정 UI에 재시작 요구를 표시한다. 기존
`@tauri-apps/plugin-process`의 `relaunch`는 사용자가 명시적 버튼을 누른 경우에만
호출한다. 성공 응답의 `BoardFile`로 Zustand를 한 번 hydrate하고, 교체로 사라진
위젯의 캐시는 기존 고아 캐시 정리 경로로 제거한다.

### UI와 오류

`보드` 설정 탭은 내보내기와 가져오기 버튼을 분리한다. 가져오기 미리보기는 모드 선택, 요약, 앨범 경고, 최종 확인 버튼을 제공한다. 교체는 현재 구성이 사라진다는 파괴적 경고를 명시한다. 취소는 오류가 아니며, 파싱·검증·저장 실패는 설정 탭 안에 원문과 함께 남긴다.

### 테스트

- export 봉투가 board만 포함하고 비밀·Todo·캐시 필드를 표현할 수 없는지 검증한다.
- import 스키마와 보드 불변식 검증을 테스트한다.
- 교체와 병합, ID 전면 재발급, 이름 충돌, 활성 보드 선택을 테스트한다.
- 원자 저장 실패 시 메모리와 기존 파일이 보존되는지 테스트한다.
- 앨범 경로 경고, 폴더→파일·파일→폴더·중첩 경로 membership, pure pattern 검증,
  저장 실패 시 live scope 불변, membership 변경의 typed relaunch 신호를 테스트한다.
- pending save flush 순서, 정확히 한 번의 hydrate, visible restart requirement와
  명시적 relaunch rejection을 React 테스트로 검증한다.
- 실제 앱 실행과 OS 다이얼로그 수동 테스트는 수행하지 않는다.
